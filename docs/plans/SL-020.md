# Plan: model divisions, seasons, and configurable sections

The owner approved this plan interactively on 2026-11-18, together with the D-01 resolution in `docs/decisions/D-01-division-season-mapping.md`.

## Issue
A division is a free-text string (`mens`, `womens`, `freshers`, and `inter` on matches). Check constraints on `teams`, `matches`, `team_registrations` and `polls` pin those values, and about 30 backend and frontend files branch on them. Adding a division or running a second season would need code and schema changes.

## Evidence
- `20261106000000_baseline.sql` has check constraints `teams_division_check`, `matches_division_check`, `team_registrations_division_check` and `polls_division_check` that list fixed values.
- `league_standings` and `top_scorers` partition by the division string.
- API routes (`home/dashboard`, `standings`, `leaderboard`, `teams`, `admin/*`) default to `'mens'` and hard-code `'freshers'`.
- No table holds division or season identity, configuration, status, ordering or visibility.

## Scope
Expand only. Legacy columns, constraints, views and routes stay unchanged.
1. New tables:
   - `divisions` and `seasons` (identity, display name, dates, status, ordering, visibility, archiving, branding, rules, format);
   - `section_types`, a lookup table of section kinds;
   - `season_sections` (enabled, nav visibility, order, settings);
   - `team_entries`, a team's participation in a season;
   - `legacy_division_map`, used only during the expand period.
2. `matches.season_id` and `team_registrations.season_id`. `team_registrations.division` becomes nullable.
3. `backfill_legacy_divisions()` follows D-01 and is idempotent. The migration and the seed both call it.
4. Compatibility triggers fill the missing side of `division` ↔ `season_id`. `teams` inserts add a team entry, insert-only. `division_model_drift()` reports disagreements.
5. `is_dictator()` and RLS:
   - Public read covers public, non-archived rows.
   - Only dictators write.
   - Archiving is separate from deletion, and RESTRICT foreign keys block deleting a season that has data.

6. **Dashboard flow (owner scope correction 2026-11-19, rule R10).** Database and API support alone is not complete. Add a minimal Divisions & Seasons tab to the existing dictator dashboard, following its patterns, with no dashboard redesign:
   - The tab is offered to a stored dictator only. RLS still decides every write.
   - Divisions: create, edit name and visibility, archive or restore, and delete (refused and explained when the division has data).
   - Seasons: create (with the default sections), edit, make current through `public.set_current_season` (migration `20261120000000`, one step, dictator only, refuses archived seasons), archive or restore.
   - Sections of a season: enabled, in navigation, order, and settings (validated as a JSON object).
   - Every view handles loading, empty, success and error states.

7. **Full port and contract (owner instruction 2026-11-19).** Production has only the three divisions, with 2026 data. Every page and data path is ported, and the legacy paths are removed once their callers are ported:
   - `backend/lib/scope.ts` resolves `?division=<slug>&season=<slug|id>` (default: the current season). The home dashboard, standings, teams, statistics, legends, fantasy leaderboard and admin match, team and registration routes use it. Captain branding finds the registration through its season.
   - `division_flairs` replaces the mens and womens flair columns, and `season_player_stats` replaces `top_scorers`.
   - In the frontend, the `LeagueContext` division is a slug and each division keeps a season choice. `useApi` scopes requests to the division and season. The admin tools list divisions from data, and the profile has one club per division.
   - The homepage shows a season dropdown when a division has more than one season. Its routes are `/<division>/<season>`, and an unknown season reports "Season not found".
   - `20261122000000` drops the legacy columns, flairs, triggers, map, views, and the unused `polls`/`poll_options`/`increment_vote`, behind guards that stop it unless every record survives. The dead components that only served them are deleted.

8. **Everything season-scoped (owner instruction 2026-11-19).** `20261123000000` places every player on its team's 2026 roster entry. It replaces `user_profiles.points` with per-season points (`season_fantasy_points`, and `season_fantasy_leaderboard()` for the public totals), and stops if any real account's stored total differs from its graded predictions. Grading no longer writes a total. Schedule, players, player profile, prediction history, the fantasy leaderboard and the home fantasy leaders are scoped to the season, and the Rules page shows a season's `rules_md`. The scope decisions are in D-01 ("Season or division").

Out of scope:
- person identity (SL-021), match events (SL-022), phases and brackets (SL-023), roles (SL-024), audit history (SL-025), API contracts (SL-026);
- the dashboard UI and lifecycle service (SL-040, SL-092), polls (SL-060), per-division flair (SL-043);
- moving readers to `season_id` (Phases 4–5), route consolidation (SL-091), the contract step (SL-102).

## Acceptance checks
- C1: The existing values are ordinary division rows, every populated legacy row maps to a season with counts preserved, `inter` creates nothing, and re-running the backfill is a no-op.
- C2: Season names and dates follow D-01.
- C3: Through the real local Auth and Data API, a dictator creates Inter with two coexisting seasons and sections, with no code or schema change. The other roles and anon are refused, and hidden or archived rows stay private.
- C4: The new model has no per-division enum or value constraint, and World Cup tables are untouched.
- C5: Archiving is distinct from deletion.
- C6: Legacy writes stay in sync and the drift report is empty.
- C7: Existing API and frontend groups still pass.
- C8 (owner): the staging deploy applies the migration and seed, and the staging checks pass.
- Dashboard flow: the component's states and writes (mocked); the real UI → Data API → database path locally and on staging, allowed and denied; `set_current_season` in pgTAP; the owner uses the tab against staging.

## Rollback
The dashboard tab is one component and one tab entry: reverting that commit removes it without touching data. `set_current_season` can be dropped by a later migration once nothing calls it.

The migration only adds. Rolling back application code is safe because legacy columns are still written and read. A defect is fixed by a new forward migration. The new tables and columns can be dropped in a later migration while nothing reads them yet, because no existing reader depends on them.
