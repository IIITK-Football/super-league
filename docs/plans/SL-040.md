# Plan for SL-040 — Division and season configuration

## Issue

Divisions and seasons must be configurable data with a safe lifecycle, so the dictator can create, publish, hide, archive, restore and order them and configure each season's sections without any code change. The schema already has the core of this:
- `divisions`, `seasons`, `season_sections` and `section_types`;
- visibility, archiving and sort order;
- one current season per division (`seasons_one_current_per_division`);
- dictator-only RLS and audit triggers.

Against the item's scenarios, it lacks:

1. **Visibility defaults.** New divisions and seasons default to `public`; they must start **hidden**.
2. **Current-season rule.** `set_current_season` accepts a hidden season, and hiding or archiving the current season does not clear `is_current` in the same write.
3. **Atomic creation and Worker writes.** Season creation is two browser writes (the season, then its default sections), so a failure can leave a season without sections. Every dashboard write goes straight from the browser to the Data API; the item wants audited, caller-scoped Worker writes, with those direct writes retired.
4. **Public use of sections.** The public site never reads `season_sections`:
   - navigation is hard-coded in `frontend/src/components/TopNavbar.jsx`, including a division-name branch (`division === 'wsl' || 'freshers'`);
   - routes exist only for three hard-coded divisions in `frontend/src/App.jsx`;
   - a disabled section's page and API stay reachable.
5. **Missing pieces.** No public season picker, no "No public seasons yet." state, no editable section labels, no reordering of divisions or seasons.

## Evidence

- **Schema, read on the local stack (2026-11-26):**
  - columns: `divisions` (visibility, archived_at, sort_order, branding), `seasons` (status, visibility, archived_at, is_current, sort_order, format, rules_md), `season_sections` (enabled, nav_visible, sort_order, settings);
  - `section_types`: overview, fixtures, standings, bracket (off), teams, team_builder (off), stats, fantasy, news, video (off), rules, registration (off);
  - RLS: the public read policies hide hidden and archived divisions and seasons, and a hidden division hides its seasons; dictators manage everything.
  - Audit triggers are on all three tables. `set_current_season(p_season)` exists and refuses archived seasons only.
- **Dashboard:** `frontend/src/components/admin/ManageDivisions.jsx` writes directly. It inserts and updates divisions and seasons, upserts and inserts `season_sections`, and calls `set_current_season` and `refresh_captain_grants`.
- **Public:** `LeagueContext` reads the division and its visible seasons; `useDivisions` lists visible divisions; the navbar is hard-coded.
- **Reusable from Phase 3:**
  - `requestClient` and `handleError`;
  - `resolveScope`, a single round;
  - round counting (`api/test/route-rounds.test.ts`);
  - parity tooling (`scripts/parity/lib.mjs`) and the browser walkthrough pattern (`scripts/ui-walkthrough/parity.mjs`).

## Scope

1. **Migration `20261206000000_division_season_lifecycle.sql`** (forward-only):
   - **Defaults:** new divisions and seasons default to `visibility = 'hidden'`; existing rows keep their values.
   - **Current-season constraint:** CHECK `seasons_current_is_public`, `NOT is_current OR (visibility = 'public' AND archived_at IS NULL)`.
   - **Same-write clearing:** a BEFORE UPDATE trigger clears `is_current` when a season becomes hidden or archived.
   - **`set_current_season`** refuses a hidden or archived season (22023).
   - **Section labels:** `season_sections.label text NULL` (1–40 characters; null means the type's label).
   - **Functions:** all SECURITY INVOKER (dictator RLS applies) with an explicit `is_dictator()` check (42501):
     - `create_division(...)`: hidden, placed last;
     - `create_season(p_division, p_slug, p_name, p_starts_on, p_ends_on, p_format)`: a hidden season plus its default sections from `section_types`, in one transaction;
     - `update_division(p_division, p_fields jsonb)` and `update_season(p_season, p_fields jsonb)`: validated fields, visibility, archive and restore (restore returns to hidden). `update_season` refreshes captain grants in the same call.
     - `reorder_divisions(uuid[])` and `reorder_seasons(p_division, uuid[])`;
     - `save_season_sections(p_season, jsonb)`: label, enabled, nav visibility and order for all sections at once.
2. **Worker routes** (caller-scoped, so the audit actor is the dictator), under `backend/app/api/admin/divisions/**` and `admin/seasons/**`, mounted in `api/src/routes.ts`:
   - divisions: `POST /admin/divisions`, `PATCH` and `DELETE /admin/divisions/:id` (the delete moves here), `PUT /admin/divisions/order`;
   - seasons: `POST /admin/seasons`, `PATCH /admin/seasons/:id`, `POST /admin/seasons/:id/current`, `PUT /admin/seasons/:id/sections`, `PUT /admin/seasons/order`.
3. **Sections enforced publicly:**
   - `resolveScope(supabase, params, { section })` embeds the season's sections in its single query. A disabled section answers 404 "This section is not available for this season"; a missing row falls back to the type's default.
   - Route mapping: dashboard → overview, schedule → fixtures, standings → standings, teams and players → teams, leaderboard → stats, predictions → fantasy.
   - Modules not yet shipped (bracket, video, registration, team_builder) keep their current behaviour.
4. **Public frontend:**
   - **Routes:** generic `/:division` and `/:division/:season` replace the three hard-coded routes; an unknown or hidden division shows not-found.
   - **Division page:** shows the current season when it is visible and unarchived. Otherwise it shows a season picker, or "No public seasons yet." when there are none. An explicit season URL opens that public season.
   - **Navigation:** `TopNavbar` builds its rows from the selected season's enabled, nav-visible sections, in their order and labels, without the division-name branch.
   - **Section gate:** `SectionGate` shows "not available" on a disabled section's page. An enabled section hidden from navigation still works by direct URL.
5. **Dictator UI** (`ManageDivisions.jsx`, existing patterns, no redesign):
   - list and detail views with Hidden, Public and Archived state labels;
   - publish, hide, archive and restore beside the state, and make current;
   - up/down ordering for divisions and seasons;
   - a section list with editable label, Enabled, Show in navigation, and up/down.

   Writes go through the Worker routes; reads stay direct under RLS. Loading, empty, success and error states throughout.
6. **Register:** the new routes are added to `docs/contracts/worker-compatibility.md`.

Versioned rules belong to SL-044; competition calculation to SL-054.

## Acceptance checks

C1 (owner) holds when the four scenarios pass, locally and on staging, through the real dictator UI, Worker and public pages:

1. **New divisions and seasons.** In a new data-driven division and in an existing one, create two seasons. Both the division and the seasons start hidden. Publish each independently. Make a visible, unarchived season current in one action. The other public season stays reachable by its URL.
2. **Hiding and archiving.**
   - Hiding or archiving the current season clears its current flag in the same write, and the public division opens the picker.
   - Restore returns a season to hidden; showing it and making it current are separate, explicit steps.
   - Hiding the division hides all its children publicly but keeps their configuration. The dictator still sees the history.
3. **Sections.** A disabled section is unavailable both as a route/API and as a navigation entry. An enabled section removed from navigation still works by its URL.
4. **Validation and audit.**
   - Invalid input and unauthorized callers are refused.
   - A failed creation rolls back the season and its sections together; a failed update leaves the configuration intact.
   - Changes are audited with the dictator as actor, and the direct dashboard writes are retired.

## Rollback

- **Migration:** additive, except the visibility defaults and the current-season constraint, which apply to new writes only (existing data already satisfies them). The functions stay unused if older code returns.
- **Code:** restore the previous site and Worker pair ([procedure](../rollback/pages-worker-pair.md)). The previous dashboard still writes directly under the unchanged dictator RLS, so it keeps working against the new schema.
