# Plan: account-linked players and self-service player profile

**Status: draft for the owner's review (2026-11-18).** Not started. SL-042 can start only after SL-021 and SL-027 are done; their remaining checks are the owner's staging attestations (SL-021 C13 and C14, SL-027 C7). One point needs the owner's choice: which fields a player may edit (see "Self-owned fields").

## Issue
- Nothing ties a player identity to an Auth account. The only connection is the private contact email in `player_private_details`.
- A player cannot read or edit their own card.
- The dictator has no way to link, unlink, see link status or bulk-link accounts.

## Evidence
- **`players` has no account column.** Its columns are `id, first_name, last_name, image_url, overall_rating, attributes, created_at, updated_at`.
  - Only dictators write ("Dictators manage players", `20261124000000`).
  - `authenticated` still holds table-level INSERT/UPDATE, gated by RLS.
- **`user_profiles` is publicly readable, including `email`** (baseline policy "Public profiles are viewable by everyone"). If `players.user_id` were readable, anyone could map a player to an email.
- **`auth.users.email_confirmed_at`** is the verified flag. Seed users have none; the integration tests create users with `email_confirm: true`.
- **`audit_row_change`** is already attached to `players` (`audit_players`, `20261126000000`). A `user_id` change is logged as a from → to uuid, never an email.
- **`attributes` jsonb layout:** `stats`, `bio.preferredFoot` and `playStyles` (`TeamBuilder.jsx`). Play-style icons come from `frontend/src/data/playStyles.js`.
- **Portrait upload:** `/api/admin/freshers/player-image` is captain/dictator only and keyed by roster place. Storage key `players/<player_id>.png` (`backend/lib/roster/playerImage.ts`).
- **The only `select('*')` on `players`** is the count in `backend/app/api/admin/stats/route.ts`.

## Scope

### Migration `20261128000000_account_linked_players.sql` (forward-only)
- **Link column:** `players.user_id uuid NULL REFERENCES auth.users(id) ON DELETE SET NULL`, with `UNIQUE (user_id)`: one player per account, any number of unlinked players.
- **Guard trigger `players_guard_account_link`** (`BEFORE INSERT OR UPDATE OF user_id`, `SECURITY DEFINER`, `search_path ''`). When `user_id` changes:
  - it requires `is_dictator()`, or a database-owner session with no JWT claims (seed and migrations), so the server key is refused like everyone else;
  - a non-null `user_id` must belong to an account with `email_confirmed_at IS NOT NULL`;
  - clearing to NULL is also allowed when the old account no longer exists (the `ON DELETE SET NULL` path);
  - errors: `42501` for not allowed, `23514` for unverified.
- **Column privileges** (defence in depth; the trigger is the rule):
  - revoke SELECT/INSERT/UPDATE on `players` from `anon` and `authenticated`;
  - re-grant SELECT on every column except `user_id`;
  - re-grant INSERT/UPDATE on `first_name, last_name, image_url, overall_rating, attributes`;
  - change the `admin/stats` count to `select('id', …)`.
- **`my_player_id()`** (`SECURITY DEFINER`, `STABLE`): the caller's linked player. Policy subqueries run with the caller's privileges, and the caller cannot read `user_id`, so the policy needs this helper. New policy: "Linked players read their own private details" (`player_id = my_player_id()`).
- **Dictator RPCs** (`SECURITY DEFINER`, `42501` for non-dictators, revoked from PUBLIC and anon):
  - `dictator_link_player_account(p_player_id, p_user_id)` and `dictator_unlink_player_account(p_player_id)`. Unlink sets only `user_id = NULL`.
  - `dictator_search_accounts(p_query)`: verified accounts only, at least 2 characters, at most 20 rows. Returns id, email, name and any player already linked.
  - `dictator_player_links(p_player_ids uuid[])`: link status and the linked account's email for a roster.
  - `dictator_preview_account_links(p_rows jsonb)`: a read-only dry run over `{player_id, email}` rows. An empty email falls back to the stored contact email.
    - Each row gets one status: `ready`, `already_linked`, `unknown_player`, `missing_email`, `no_account`, `unverified_account`, `ambiguous_account`, `duplicate_player_in_file`, `duplicate_account_in_file`, `account_linked_elsewhere`, `player_linked_elsewhere`, `invalid_row`.
    - At most 500 rows.
  - `dictator_apply_account_links(p_rows jsonb)`: repeats the preview in the same transaction. It changes nothing if any row is not `ready` or `already_linked`.
  - Nothing is ever matched by name.
- **Self-service RPCs**, for the caller's own linked player only:
  - `player_my_profile()`: card, private email and roster places.
  - `player_update_own_profile(p_image_url, p_preferred_foot, p_play_style)`:
    - `p_image_url`: NULL, unchanged, or the caller's own key URL ending in `/players/<own id>.png`;
    - `p_preferred_foot`: Right, Left or Both;
    - `p_play_style`: a catalog name of at most 60 characters, or NULL;
    - it merges only `attributes.bio.preferredFoot` and `attributes.playStyles = [{name}]`;
    - an unlinked caller gets `42501`.
- **Audit:** no new trigger is needed. `audit_players` records link, unlink and self-edits with the actor.
- **Seed:** one verified fan linked to a seeded player, and one unverified account.

### Self-owned fields (to confirm with the owner)
- **Allowed:** portrait, preferred foot, play style. SL-003 gives players "own profile fields: U own", and these are presentation choices about the person.
- **Not allowed:** overall rating, stat values (`attributes.stats`) and position.
  - The matrix gives users "—" on FUT fields, which sit on the captain's allow-list.
  - Self-rating would make the card unreliable.
  - Position is per season, on the roster place.
- **Never:** name, roll number, email, link, roster. These are protected identity fields.
- **If the item's "FUT editing" was meant to include stat values,** add one argument; nothing else changes.

### API
- `POST /api/profile/player-portrait` (multipart `image`):
  - `requireUser`, then the caller's player from `player_my_profile`; an unlinked caller gets 403;
  - `readPortrait`/`uploadPortrait` with `portraitKey(player_id)`; returns the URL;
  - the client saves the URL through the self-service RPC.
- Play-style icons and descriptions are resolved from the catalog by name, so no player-supplied URL is stored.

### Dictator UI (Teams & Rosters)
- **Link status in the roster:** `loadRoster` also calls `dictator_player_links`. The player dropdown marks linked players, and the edit panel shows "Linked to `<email>`" or "Not linked".
- **Link and unlink:**
  - search verified accounts (at least 2 characters); results show "already linked to `<player>`";
  - Link calls the RPC; Unlink asks for confirmation;
  - `describeError` covers unverified, already linked and not allowed.
- **"Import account links" panel:**
  - paste or upload a CSV with the header `player_id,email` (pure `parseLinkCsv` validator);
  - Preview shows a per-row status table with counts;
  - Apply is enabled only after a clean preview of the same rows.
- **Why a dashboard upload rather than a local script:** the guard refuses the server key, so a script would need a dictator token and hosted credentials on the owner's machine. The dashboard runs as the dictator under the same database rules and is tested like the rest of the UI.

### Player UI (`/profile`)
- A "Your player card" section in `UserProfile.jsx`, separate from the account form:
  - **Loading:** a skeleton.
  - **Empty:** "No player is linked to your account. Ask a dictator."
  - **Linked:** read-only name, rating, contact email and seasons. Portrait upload (500 × 500 PNG), preferred foot and play-style picker are editable.
  - Save calls the RPC, with success and error messages, and is disabled while saving or unchanged.
- Extract `PlayStylePicker` from TeamBuilder for reuse.

### Out of scope
- Players claiming an account themselves.
- Division nickname and supported team (SL-043).
- The `user_profiles` email exposure (SL-025).
- Roles (SL-024).
- Card redesign (SL-095).

## Acceptance checks
- **C1 (pgTAP 009):**
  - `user_id` is nullable, unique, and `ON DELETE SET NULL`; deleting the account keeps the player;
  - several unlinked players coexist;
  - `anon` and `authenticated` cannot read `user_id`.
- **C2 (pgTAP 009 + integration):** a dictator links a verified account. Refused: an unverified account, a second player for the same account, a second account for the same player.
- **C3 (pgTAP 009 + integration):** user, captain, legacy admin, editor, anon and the server key cannot link, unlink or claim through any of these:
  - a direct Data API write;
  - `create_rostered_player` or `captain_update_roster_player`;
  - the self-service RPC;
  - any route.
- **C4:** unlink changes only `user_id`. Card, private details, roster places, goals and season stats are unchanged.
- **C5:**
  - a linked player reads their own private details and updates only portrait, foot and play style, on their own identity only;
  - rating and stats are untouched;
  - a foreign portrait URL is refused;
  - an unlinked user is refused, and so is their portrait upload.
- **C6:** link, unlink and self-edit appear in `audit_log` with the actor and `user_id` from → to. No email appears in any audit row.
- **C7:** the import preview reports every problem status and writes nothing. Apply with any problem row writes nothing. Nothing is matched by name.
- **C8:** after linking and a self-edit, the same player id and card appear in `/api/players`, `/api/players/:id`, `season_player_stats`, the leaderboard and fantasy.
- **C9 (mocked UI):**
  - ManageRosters: link status, search, link and unlink, import preview and apply, with every state;
  - `/profile` card section: loading, empty, success and error states, sending exactly the allowed fields.
- **C10 (local real stack):**
  - a dictator links and unlinks from Teams & Rosters and runs an import;
  - a linked player edits their card on `/profile`;
  - a normal user is refused and nothing is written.
- **C11 (owner, staging):**
  - the deploy applies the migration and the staging checks pass;

  - the owner signs in as that player and edits the card;
  - the owner unlinks and sees the history entries.

## Rollback
- **Data:** the migration only adds things, and unlinked players behave exactly as before. Rolling back is a forward migration that drops the RPCs, policy, trigger and column (after exporting the links) and restores the table grants. The audit history keeps every link.
- **UI:** each UI commit reverts on its own without touching data.
- **Bad bulk links:** unlink them one by one, using the audit history.
- **Production:** only through the reviewed `main` release, with a backup point.
