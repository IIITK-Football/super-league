# SL-042: Account-linked players, verified-email matching and account-first players

Revised 2026-11-19 from the owner-approved plan. The first version (account links, self-service, a CSV import) is on staging; this revision replaces the CSV import and adds automatic matching and account-first creation, as new forward migrations.

The owner finds the CSV import too basic and wants:

2. **A manual link** that finds the player through Division → Season → Team → Player.

5. **Email from Auth only:** Auth is the single source of truth for a player's email, so it can't drift.

### Owner answers (2026-11-19)
- **Legacy emails become private match keys.** An unlinked legacy player's old contact email moves to a dictator-only table. It is never displayed as a contact email and is used only to match a verified account. It is removed on link or on dismissal. The contact-email table is then dropped.
- **Link before any new roster.** Every new roster place requires a linked player: new and existing identities, across every season.

## Scope
### Data rules
1. **Auth is the only email source.**
   - A linked player's email is `auth.users.email` of the linked account, read through server functions. It is read-only for everyone, the player included.
   - An unlinked player has **no** email.
   - `user_profiles.email` is never used.
   - `player_private_details` is reduced to outcomes (no addresses) and match keys, then dropped.
2. **Normalization:** `lower(btrim(email))`, exact comparison only. Nothing is ever matched by name.
3. **Match keys:** `player_link_keys(player_id PK → players ON DELETE CASCADE, email_normalized, source 'legacy_contact', recorded_at)`.
   - Only unlinked players have keys. Keys are not unique: duplicate keys are reported, never resolved automatically.
   - Readable by dictators through functions only; no direct grants.
4. **Migration evidence without addresses (owner, 2026-11-19):** `player_email_migration_outcomes(player_id, outcome, recorded_at)`, plus a counts summary. It holds **no email address**, raw or normalized.
   - Outcomes: `linked_auth_email_same`, `linked_auth_email_differs`, `unlinked_key_kept`, `discarded_blank_or_invalid`.
   - Append-only and dictator-read.
   - The only addresses kept are the match keys of unlinked players, each deleted on link or dismissal.
5. **One-to-one, as now:** `UNIQUE(user_id)` with one column per player, and links to verified accounts only.
   - A `SELECT … FOR UPDATE` on the candidate player plus `WHERE user_id IS NULL`, and a transaction advisory lock on the normalized email, serialize concurrent links.
6. **New identities need an account.** A `BEFORE INSERT` trigger on `players` refuses `user_id IS NULL` for any request session (JWT present), which includes the server key.
   - Only sessions with no request JWT (migrations and the seed) may insert unlinked rows: the seed's legacy fixtures.
   - Table INSERT on `players` is revoked from `authenticated`.
   - The only creator is `create_player_for_account`.
7. **Roster places need a linked player.** A `BEFORE INSERT` trigger on `roster_memberships` (and on `UPDATE OF player_id`) refuses a player with `user_id IS NULL` for request sessions.
   - Existing places of unlinked players stay (history). Moving a place between teams of the same season and removing it are unchanged.
8. **Unlink** clears only `user_id`: the player then has no email and **no key is recreated**, so it can't auto-relink. Roster places, cards and history are untouched.
9. **Account deletion** keeps the player, unlinked and with no email (`ON DELETE SET NULL`, as now).
10. **Self-service is unchanged:** a player edits only their portrait and preferred foot. Their email is shown read-only from Auth.

### Flows
**A. Account matching (Teams & Rosters, replaces "Import account links").**
- **Live preview** (`account_link_matches()`, dictator-only, read-only). It shows counts and a list for each category:
  - **ready:** exactly one unlinked player key equals one verified, unlinked account's Auth email;
  - **waiting for verification:** the account exists but is unverified;
  - **no account:** the key matches no account;
  - **duplicate:** one email is the key of several unlinked players;
  - **conflict:** the account is already linked to another player.
- Each row shows the player (name and latest team/season), the account email and the reason.
- **"Link all N ready matches"** (with confirmation) calls `apply_account_link_matches(p_expected jsonb)` with the previewed `{player_id, user_id}` pairs.
  - The server recomputes the matches and links only pairs that are still ready. Anything stale or changed is skipped and reported.
  - It is idempotent; each link removes the player's key.
- **Dismiss a key:** `dismiss_player_link_key(p_player)`, used for a typo or a person who left.
- Duplicates and conflicts link to flow B to resolve by hand.

**B. Manual link (dictator).**
- **Step 1, account:** search verified accounts **by Auth email** (`verified_accounts_for_linking(p_query)`, replacing `player_link_candidates`). Each result shows whether the account is already linked, and to which player.
- **Step 2, player:** Division → Season → Team → Player, reusing the Teams & Rosters loaders (extracted into a `useRosterPicker` hook). The dropdown lists **only unlinked players**.
  - The selectors only find the player: the link is on the identity, across every roster and its history.
- **Link** calls `link_player_account` (which now also removes the player's key).
- Unlink stays in the player edit panel, with confirmation.

**C. Automatic link on verification (database).**
- **Trigger points:** `auto_link_verified_account(p_user)` (SECURITY DEFINER, empty `search_path`) runs from triggers on `auth.users`:
  - `AFTER INSERT` when `email_confirmed_at` is set (Google OAuth and admin-created confirmed accounts);
  - `AFTER UPDATE OF email_confirmed_at` going from NULL to set (email confirmation).
- **Logic:** skip if the account is already linked. Otherwise take the advisory lock on the normalized Auth email and find unlinked players whose key equals it.
  - **Exactly one:** set `user_id` and delete the key.
  - **None, or more than one:** do nothing. The case appears in flow A as unmatched, duplicate or conflict.
- **Never blocks sign-in:** the whole body runs in `BEGIN … EXCEPTION WHEN OTHERS THEN RAISE WARNING`, so a linking problem never fails registration or confirmation.
- **Guard and audit:**
  - The GoTrue session has no request JWT, so `players_account_link_guard` allows it, and the verified check holds.
  - The audit row has `actor_id` NULL and `actor_role 'auto-link'`. `audit_row_change` gains `COALESCE(claim role, current_setting('app.audit_actor_role', true), current_user)`, and the function sets that setting transaction-locally.
  - Audit History shows "Automatic link (email verified)".
- **Not triggered:** an email change on an already-linked account changes nothing (the displayed email follows Auth). There is no auto-link before verification, no name matching and no automatic player creation.

**D. New player (account first; replaces the free-form "New player" form).**
- **Step 1, account:** pick a verified account by Auth email (the same search as B).
  - **Already linked:** show "Already linked to X (latest team)" and offer **"Add X to `<team>`"** through `add_player_to_roster`. It is disabled with a reason if X already has a place this season.
  - **Not linked:** the name and card form appears. `create_player_for_account(p_user, p_team_entry_id, name, rating, card attributes, jersey, position, image)` creates the player, sets `user_id` and adds the roster place in **one transaction**.
    - It refuses (23505, with the existing player's id) if the account became linked in the meantime.
    - Nothing is half-created.
  - There is no email field: the email comes from the account.
- **Portrait:** the existing upload and save, unchanged.

**E. Add an existing player.**
- Search results for unlinked players show **"Not linked to an account: link first"** and no Add button. Add calls `add_player_to_roster(p_player, p_team_entry_id, jersey, position)` (dictator; linked players only), replacing the direct `roster_memberships` insert.

### Migrations
- **M1 `<ts>_account_email_keys.sql` (expand):**
  - **Outcomes:** one outcome row (no address) per `player_private_details` row, with a guard that the outcome count equals the source count (else abort, nothing changed).
  - **Linked players:** record the outcome (`linked_auth_email_same` / `linked_auth_email_differs`; Auth wins).
  - **Unlinked players with a usable email:** insert a key. Blank or invalid emails are recorded as `discarded_blank`.
  - **Schema:** the keys table, the two triggers, the new RPCs, the auto-link triggers, and the `audit_row_change` actor-role fallback.
  - **Lockdown:** revoke `players` INSERT and all `player_private_details` writes. `NOTICE` the counts per outcome.
- **M2 `<ts>_drop_contact_emails.sql` (contract, after callers are ported and verified on staging):**
  - drop `player_private_details`, `create_rostered_player`, the old `update_rostered_player` overload, `preview_`/`apply_player_account_links(jsonb)` and `player_link_candidates`;
  - update the inventory counts.
- **Report:** `scripts/sql/player-email-migration-report.sql` (read-only) lists migration outcomes, keys, duplicates and conflicts for the owner's rehearsal on a local production-shaped copy. It replaces `player-account-link-candidates.sql`.
- **Rollback:**
  - links are reversible by unlink;
  - auto-link can be switched off by a forward migration that drops its two triggers;
  - addresses are deliberately not retained: a linked player's email is the Auth email, and an unlinked player's is the match key. Dropping the contact-email table (M2) is irreversible by design, so it runs only after the outcomes report has been reviewed.
- **Seed** (idempotent; no-JWT session):
  - a key for a verified seed account (ready match);
  - two players sharing one key (duplicate);
  - a key for an unverified account (waiting);
  - a key matching an account already linked elsewhere (conflict);
  - a key with no account;
  - `fan01` stays linked to Jackson Lamb;
  - `verify-preview.sql` gains "no key belongs to a linked player" and "no player has contact details outside Auth".
- **Production:** nothing now. The migrations go to production only through the owner's `main` PR, after the report is rehearsed on a production-shaped copy.

## Risks
- **Hidden player creators:** fixtures and scripts that insert players with the server key will fail. Mitigation: the scan test, porting every fixture, and the fake staging updated first.
- **Auth trigger safety:** a bug in the auto-link must never stop sign-ups. Mitigation: the exception wrapper, and a test that forces an error and still confirms.
- **The GoTrue session might carry JWT claims:** if so, the guard would refuse the auto-link. Mitigation: the C14 staging check confirms a real account through GoTrue; if claims appear, the function uses a transaction-local allow flag that only it sets.
- **Legacy data quality** (typos, shared emails): never resolved automatically. They are reported as duplicates or no-account, and the dictator resolves or dismisses them.
- **Unlinked legacy players can't join new rosters** (your choice): seasons may wait on account verification. The matching panel and manual link are the way through.
- **Production:** the outcomes report must be rehearsed on a production-shaped copy before the `main` PR; no production action is part of this item.
