# Plan: account-linked players and self-service player profile

**Status: approved by the owner 2026-11-19; in progress.** It replaces the 2026-11-18 draft.

## Issue
A player identity (`players`, the reusable FUT card shared across seasons) has no link to an Auth account. The only tie is a dictator-entered contact email in `player_private_details`. So a person can't edit their own card, and dictators can't link or unlink accounts or bulk-link them. SL-042 adds a verified, dictator-controlled one-to-one link and a minimal self-service card editor on `/profile`, enforced in the database on every write path.

**Owner decisions (2026-11-19):**
- **One play style per player:** a single catalog value everywhere, or none ("not set"). No arrays and no array compatibility in the database, API, seed or UI; production holds one play style per player.
- **SL-042 self-service:**
  - a player edits **only** their portrait and preferred foot;
  - never name, rating, stats or play style (play style stays with captains for their own team, and dictators);
  - a portrait update goes live immediately and is audited.

### Part 1: account links and self-service
### 1. Data model and enforcement (migration `<ts>_account_linked_players.sql`, forward-only)
- **Link column:** `players.user_id uuid NULL REFERENCES auth.users(id) ON DELETE SET NULL` plus `UNIQUE (user_id)`.
  - **One player per account:** the unique key.
  - **One account per player:** a single column.
  - **Any number of unlinked players.** An account deletion clears the link and keeps the player.
- **Guard trigger `players_account_link_guard`** (`BEFORE INSERT OR UPDATE OF user_id`, security definer, empty `search_path`). It runs on **every** path, including the server key:
  - **Who:** the change is allowed only if `public.is_dictator()`, or for a database session with no request JWT (migrations and seed). `service_role` has a JWT role and no dictator `sub`, so it is refused.
  - **Account deletion:** clearing to NULL is allowed when the old account no longer exists (the `ON DELETE SET NULL` cascade).
  - **Verified only:** a non-null target must have `email_confirmed_at IS NOT NULL`.
  - **Errors:** `42501` "Only a dictator can link a player to an account"; `23514` "Only a verified account can be linked"; the unique key gives `23505` "That account is already linked to another player".
- **Column privileges** (defence in depth; the guard is the rule):
  - revoke table SELECT, INSERT and UPDATE on `players` from anon and authenticated;
  - grant SELECT on every column **except `user_id`**;
  - grant INSERT and UPDATE on `first_name, last_name, image_url, overall_rating, attributes` (dictator writes still pass RLS);
  - fix `admin/stats` to `select('id', …)` in the same commit.
  - Public pages can never map a player to an account.
- **Dictator RPCs** (security definer, empty `search_path`, `is_dictator()` or 42501; EXECUTE for authenticated only):
  - `link_player_account(p_player uuid, p_user uuid)` and `unlink_player_account(p_player uuid)`. Unlink sets only `user_id = NULL`; card, private details, roster places and history are untouched.
  - `player_link_candidates(p_query text)`:
    - verified accounts only, any of the name or email words matching (as `account_directory`);
    - returns `(user_id, label, linked_player_id, linked_player_name)` with the label = the verified Auth email and name, as in `account_directory`;
    - never a profile email or raw id in the label.
  - `player_link_status(p_player_ids uuid[])`: per player, linked or not and the linked account's label.
  - **Bulk import:**
    - `preview_player_account_links(p_rows jsonb)`: rows `{player_id, email}`, at most 500, read-only. It matches the email to **verified Auth emails only** (case-insensitive, trimmed) and never by name. Statuses:
      - `ready`, `already_linked` (same pair);
      - `unknown_player`, `missing_email`, `invalid_row`;
      - `no_account`, `unverified_account`;
      - `duplicate_player_in_file`, `duplicate_account_in_file`;
      - `account_linked_elsewhere`, `player_linked_elsewhere`.
    - `apply_player_account_links(p_rows jsonb)`: recomputes the preview in the same transaction and writes **nothing** unless every row is `ready` or `already_linked`. It is idempotent.
    - **Contact email:** the dictator chooses which email is used. A blank email in the file may fall back to the player's dictator-entered contact email (`player_private_details`, which is not user-editable); that row's status names the source.
- **Self-service RPCs** (security definer; the caller's own linked player only; an unlinked caller gets 42501):
  - `my_player()`: the caller's card (canonical fields), their own contact email and their roster places (season, team, jersey, position). The caller can't read `user_id` directly, so the RPC resolves it.
  - `update_my_player(p_image_url text, p_preferred_foot text)`:
    - **Portrait:** `p_image_url` is unchanged, NULL to remove, or a URL whose key is exactly `players/<own player id>.png` under the configured media base.
    - **Foot:** `p_preferred_foot` is Right, Left, Both or NULL (not set).
    - **Merge:** only `bio.preferredFoot` is merged into `attributes`; every other key is kept. The canonical check validates the result.
    - **Untouched:** rating, stats, play style, name and roster fields.
- **Audit:** no new trigger. `audit_players` records link, unlink and self-edits with the actor (dictator or the player); emails never appear. The pgTAP test asserts it.
- **Seed (deterministic and idempotent):** one **verified** fan account linked to a seeded player, and one **unverified** account to show the refusal.
  - **Staging:** the seed runs there too, but it only adds synthetic accounts and never changes real users.
  - **The seed check** (`verify-preview.sql`) gains "every linked account is verified".
- **Data review (no production access assumed):**
  - add a read-only `scripts/sql/player-account-link-candidates.sql`. It lists players whose contact email matches a verified account, plus duplicate contact emails, as a starting file for the import preview;
  - the owner runs it on a local production-shaped copy;
  - **no automatic links are created by the migration.**

### 2. API
- **`POST /api/profile/player-portrait`** (multipart `image`): requires a signed-in user. It resolves the caller's player through `my_player()`; an unlinked caller gets 403. It uses `readPortrait`/`validatePortrait`/`uploadPortrait` with `portraitKey(own id)` and returns the URL. The client then saves it through `update_my_player`, so nothing is saved until the RPC succeeds.
- **No other route writes `user_id`.** A repository test scans `backend/app/api` and `backend/lib` for `user_id` writes on `players`, like the legacy-admin scan.

### 3. Dictator UI (Teams & Rosters, minimal, current patterns)
- **Player edit panel:**
  - "Account: `<label>`" or "Not linked", from `player_link_status`, loaded with the roster;
  - **Link:** an account search box (debounced, the `useLatestSearch` hook). Results show "already linked to `<player>`", disabled. Link calls the RPC, then reloads.
  - **Unlink:** asks for confirmation, then reloads;
  - **States:** loading, no match, error with retry; messages for unverified, already linked and not allowed;
  - a linked marker in the player dropdown.
- **"Import account links" (collapsible):**
  - paste a CSV with the header `player_id,email`, validated by a pure `parseLinkCsv`;
  - **Preview** shows a per-row status table with counts;
  - **Apply** is enabled only after a clean preview of the same text, then reloads.

### 4. Player UI (`/profile`, minimal)
- **A "Your player card" section,** separate from the account form:
  - **Loading:** a skeleton.
  - **Empty:** "No player is linked to your account. Ask a dictator to link it."
  - **Linked:**
    - the shared `FutCard` previews the draft live, including a local portrait preview before upload, then the saved picture, with retry on a failed upload;
    - read-only name, rating, stats and seasons (team, jersey, position per season);
    - editable: portrait and preferred foot only; play style, rating and stats are shown read-only;
    - Save is disabled while saving or unchanged, with success and error messages.
- **PlayerProfile (Clubs)** resolves play-style icons from the catalog when a stored style has only a name. `FutCard` already does.

## Risks
- **Column privileges:** any future `select('*')` on `players` by anon or authenticated fails. The repository scan and the inventory test catch it.
- **Guard bypass via the server key:** the guard refuses JWT sessions without a dictator, including `service_role`. An unexpected database-owner path (not used by the app) could still write the column; tests pin this.
- **Verified state on staging:** real staging accounts may be unverified, so the staging checks create their own verified synthetic accounts.
- **Self-edited portraits are public.** There is no moderation step (question 1).
- **Bulk import ambiguity:** duplicate contact emails across players are reported and never auto-resolved.

## Rollback
- **Data:** the migrations only add things (column, guard, functions), apart from the play-style data move.
  - The play-style move is reversible by a forward migration, since each array held exactly one name: the guard proves it, so nothing is lost.
  - Unlinked players behave exactly as before.
- **Rolling back:** a forward migration drops the link functions, policy, trigger and column (after exporting the links) and restores the table grants. The audit history keeps every link.
- **UI commits** revert on their own without touching data.
- **Bad bulk links:** unlink them one by one, using the audit history.
- **Production:** only through the reviewed `main` release, with a backup point.
