# Plan: stable API contracts independent of the current UI

**Status: draft (2026-11-18).** It starts after SL-025 and describes the final Phase 2 model. Parts marked **[dep]** depend on unfinished work:
- identity and rosters: SL-021 (in progress);
- audit history: SL-027 (in progress);
- scoped roles: the SL-024 draft, pending D-03;
- match events: the SL-022 draft, pending D-08;
- account links: the SL-042 draft;
- registration: SL-045;
- World Cup: D-02.

A different answer changes that domain's contract and schemas, but not the URLs or conventions. The contract assumes only that a handler maps a `Request` to a `Response`, so it does not depend on the D-04 and D-05 proposals.

## Issue
- There are 54 route handlers, each with a route-specific response shape, and World Cup has its own namespace.
- The frontend depends on those shapes. It also makes about 70 direct Data API calls, including privileged writes such as `user_roles`, the roster RPCs and `goals`.
- No contract exists that the Worker port (SL-030 to SL-032) can be checked against.

## Evidence
- **Inventory:** 54 handlers (`docs/plans/SL-029.md` §D): 26 World Cup, 9 public division reads, 8 management, 6 predictions, 3 newsletter, 1 auth, 1 media.
- **Three error shapes are in use:**
  - `{success:false,message}` (`lib/errorHandler.ts`, `scopeErrorResponse`);
  - `{error}` (about 50 call sites);
  - `{success:false,error}` (World Cup).
- **Pagination** exists only in `news` (`page`/`limit`). The season fantasy leaderboard RPC has a fixed limit of 100.
- **Scope** (`lib/scope.ts`):
  - `division` is a slug and defaults to `super-league`;
  - `season` is a slug or id and defaults to the current season;
  - a malformed value gives 400, and an unknown or hidden one gives 404.
- **Authorization varies by route:**
  - single-role lookups (team registrations, newsletter, live scoring, player image);
  - "any signed-in user" (`admin/stats`, `matches/update`);
  - a `user_id` taken from the request body or query under the secret key (`wc/flair`, `wc/predictions/*`);
  - no authentication on `wc/sync/manual`, `wc/sync/brazil` and `wc/test`.
- **Frontend Data API calls:**
  - divisions, seasons and their sections, `set_current_season`;
  - `team_entries`, teams, players, roster memberships, private details, and the roster RPCs;
  - matches, goals and team registrations;
  - `user_profiles`, `user_roles`, `audit_log`, `division_flairs`, `wc_teams`;
  - Auth calls.
- **Unused routes:** no frontend caller was found for `auth/login`. `wc/test` is a debugging route.
- **Tests:** existing tests call handlers in-process (`backend/tests/divisions/*`). `api-services` is pending.

## Scope

### 1. Deliverable format
- **Contract documents:** one versioned document per domain, `docs/contracts/v1/<domain>.md`, covering accounts-roles, divisions-seasons, teams-players, matches-events, standings-stats, fantasy, editorial-home, media and world-cup (isolated). Each gives endpoints, access class, rule, schemas, errors, examples and **[dep]** markers.
- **Schemas:** Zod schemas in a new workspace package `packages/contracts`:
  - `src/v1/<domain>.ts`;
  - `src/legacy/<route>.ts`, which pins today's shapes for compatibility;
  - `src/inventory.ts`.
- **Why Zod rather than OpenAPI:** Zod is already a backend dependency; the same schemas validate in Hono and Next and type the frontend; OpenAPI can be generated later if needed. A hand-written OpenAPI file would be a second source of truth.
- **Versioning:** targets live under `/api/v1/...`. Breaking changes create v2; additive fields are allowed within a version.

### 2. Conventions (v1)
- **Success:** `{ data, meta? }`.
- **Errors:** `{ error: { code, message, details? } }`.
  - Codes: `bad_request` (400), `unauthenticated` (401), `forbidden` (403), `not_found` (404), `conflict` (409), `payload_too_large` (413), `locked` (423, World Cup deadlines), `unavailable` (503), `internal` (500).
  - Messages never contain database text.
- **Pagination:** `?limit` (default 20, maximum 100) and an opaque `?cursor`; `meta.nextCursor` in the response. Naturally bounded lists (standings, one match's events) are not paginated.
- **Scope:**
  - division reads take `?division=<slug>&season=<slug|id>`, with `division` required and `season` defaulting to the current season;
  - the 400/404 rules stay unchanged;
  - writes take `season_id` or `team_entry_id` in the body, never slugs.
- **Identity** always comes from the token. No v1 endpoint accepts a caller's `user_id`.

### 3. Access classes
- **public:** anonymous, intentionally public data only.
- **account:** signed in, own rows only.
- **privileged:** a role or assignment (`dictator`, `editor`, `captain_of(entry)`, `can_score(match)` **[dep SL-024]**), or a cron secret.
- **Enforcement:** RLS and RPCs stay the database enforcement; the API checks the same rule explicitly and returns 403.

### 5. Compatibility during SL-032
- Every current `/api/*` path keeps its method, query parameters, status codes and pinned legacy schema until the Phase 9 frontend migration. In the Worker, each is an adapter over the v1 handler.
- A legacy path is retired only after its last frontend caller is gone and the drift test confirms it.
- Direct Data API calls marked "change" keep working under RLS until their page moves to v1.

## Acceptance checks
- **C1:**
  - every `backend/app/api/**/route.ts` handler and method, and every `supabase.from`/`rpc`/`auth` call in `frontend/src`, has exactly one inventory row with a class, a rule and a status;
  - every v1 target has a schema.

  Verify: `test:backend/tests/contracts/inventory.test.ts`
- **C2:** against the `next` target and local Supabase, each kept or changed route matches its pinned legacy schema, applies the scope rules (400 and 404), and shows allowed and denied cases for every access class. Verify: `test:backend/tests/contracts/legacy-compat.integration.test.ts`
- **C3:** v1 schemas accept the documented examples, reject malformed ones, and use the error and pagination conventions. Verify: `test:packages/contracts/test/schemas.test.ts`
- **C4 (owner):** the owner has reviewed the contract documents, the inventory and the compatibility rules. Verify: `manual:owner`

## Tests
- **`backend/tests/contracts/target.ts`** exports `call(request)` for two targets with the same signature, so one suite runs against both:
  - `next` (default) calls the imported Next handler in-process;
  - `worker` (added by SL-030) calls the Hono app's `fetch`.

  `SL_API_TARGET` selects the target.
- **Activate `api-services`** (owner-confirmed gate file):
  - tests: `backend/tests/contracts/**` and `packages/contracts/test/**`;
  - covers: `packages/contracts/src/**`, `backend/lib/scope.ts`, `backend/lib/errorHandler.ts`.
- **Regression:** `divisions`, `rosters`, `auth-identity`, `audit` and `config` stay green.

## Commits
1. `docs(api): add versioned domain contracts and route inventory`
2. `feat(contracts): add shared zod schemas for v1 and pinned legacy shapes`
3. `test(api): check the route and data-access inventory for drift`
4. `test(api): run contract tests against a selectable API target`
5. `chore(test): activate the api-services test group`

## Rollback
The change adds documents, a package and tests only. No route, schema or migration changes, so reverting the commits restores the previous state. If activating `api-services` blocks unrelated work, revert only the last commit: the group returns to pending and the documents stay.
