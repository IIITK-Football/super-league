# Plan: five roles with scoped captain and scorer assignments (full port)

**Addendum 2026-11-20:** a captain assignment is writable while its season is current or upcoming (`planned`/`registration`) and not completed or archived, so a captain can prepare a future season; branding stays team-level; the grant lapses in the dictator-only season-lifecycle RPCs, never a trigger (see the D-03 addendum). Where this plan says "active while its season is current", the addendum wins.

**Status: draft; D-03 resolved by the owner 2026-11-19 (`docs/decisions/D-03-roles-and-assignments.md`).** This plan follows that decision; where it differs from the proposal's defaults (Q4, Q5) the decision wins and this plan has been updated. Migration timestamps are assigned when the item starts.

If an answer differs, these parts change:

## Issue
- `editor` is a legacy single-role value. (Fixed 2026-11-19: `admin`, once labelled Scorer with dictator powers, now grants nothing and is retired.)
- A user holds exactly one role (`user_roles` has primary key `user_id`).
- Captain assignment is `team_registrations.captain_id`, unique across all seasons.
- Changing a captain fails with `team_registrations_pkey`: the upsert uses `onConflict: 'captain_id'` while sending the existing `id`.
- No scorer is stored. `POST /api/admin/matches/live` admits `dictator` **and `captain`**, so any captain can score any match (`admin` removed 2026-11-19).
- Baseline policies let any signed-in user write `matches`, `goals`, `teams` and `newsletter`.

## Scope

### Migration A `<ts>_roles_and_assignments.sql` (one transaction; stops on the first failed guard and changes nothing)
1. **Guards:**
   - every registration has a team and a matching team entry;
   - no captain holds two registrations in one season;
   - snapshot the per-role counts.
2. **Grants:**
   - assert no `admin` row remains (`20261130000000`), then delete the `default` rows (audited, with the migration as actor);
   - change the primary key to `(user_id, role)`;
   - CHECK `captain/scorer/editor/dictator`;
   - add `granted_by` and `granted_at`.

   Postcondition: the captain, editor and dictator counts are unchanged. No legacy `admin` is re-granted (owner decision 2026-11-19, SL-004 §3a).
3. **Assignment tables:** `captain_assignments` and `scorer_assignments`, as in D-03 §3. RLS: read your own rows, or all rows as a dictator; only dictators write.
4. **Backfill:** `team_registrations` → `captain_assignments` (`assigned_at = created_at`), with equal counts and identical `(captain, team, season)`.
5. **Team names:** `teams.name` stays authoritative and is never overwritten. Differing registration names are copied into `legacy_team_registration_names` (dictator read) and reported; the captain or a dictator renames the team deliberately.
6. **Helpers** (`STABLE SECURITY DEFINER`, empty `search_path`, authenticated only):
   - `has_role(text)`, with `is_dictator()` redefined on top of it;
   - `is_captain_of(entry)`, `can_score(match)` (honours expiry), `my_roles()`, `scorable_match_ids(uuid[])`.

   Drop `is_role_manager`, `handle_new_user_role` and its trigger, and `enforce_team_logo_and_color` (the route checks logo and colour instead).
7. **Dictator RPCs** (SECURITY INVOKER):
   - `assign_captain(entry, user)` inserts or **updates** the entry's one row (no co-captains) and adds the captain grant (an editor keeps the editor grant). A person may captain several entries across seasons and divisions; there is no per-user or per-season uniqueness. When the previous captain no longer has a writable captain assignment, only their `captain` grant is removed; other grants and the audit history stay.
   - `assign_scorer(user, season, match, expires_at)` adds the scorer grant.
   - Revoking an assignment removes the matching grant only when it was the person's last writable assignment of that kind (current or upcoming, not completed or archived; D-03 addendum); other grants are never touched.
   - A trigger refuses removing the last dictator grant.
8. **Policies:**
   - `user_roles`: read own rows or as a dictator; dictator writes only.
   - `matches`: insert and delete by dictator; update by a dictator or `can_score(id)`.
   - `goals`: writes by a dictator or `can_score(match_id)`.
   - `teams`: dictator writes; captains change their team through the route.
   - `newsletter`: insert and update by editor or dictator; delete by dictator.
   - `polls` and `predictions`: dictator.
   - Drop the `USING (true)` write policies on these tables. The wider audit stays in SL-025.
9. **`captain_update_roster_player`:** a dictator, or the captain grant plus a captain assignment on the place's team entry. Error strings unchanged.
10. **Audit:** recreate `audit_user_roles` with keys `user_id,role`, and attach the audit trigger to both assignment tables and the names snapshot.

### Migration B `<ts>_retire_team_registrations.sql` (last commit)
- **Guard:** every registration has an identical assignment, and every differing name is snapshotted.
- **Then drop** `team_registrations`. The owner may hold this migration to a later production release (SL-004 rule 4).

### API
- **`backend/lib/auth/roles.ts`:** `requireUser`, plus `can(…)` over the helper RPCs, called as the caller.
- **Live route:** a dictator or `can_score(match_id)`, otherwise 403. The captain branch is removed (the admin branch already was, 2026-11-19).
- **`GET /api/admin/matches`:** for non-dictators, only scorable matches.
- **Newsletter:** create, edit and upload by an editor or dictator; delete by a dictator.
- **Player image:** a dictator, or `is_captain_of(entry)` (a writable assignment, D-03 addendum).
- **Team details (generalised from team branding):**
  - name, short name, colour and logo for the captain's team entry, in every division;
  - validated, then written with the server key after the check.
- **Delete `admin/team-registrations`.**

### Frontend (existing patterns, no redesign)
- **AuthContext:** `roles` from `my_roles()` and `hasRole()`. The single `role` goes (the admin mapping already went, 2026-11-19).
- **Login:** destinations in the order dictator, captain, editor, scorer.
- **RoleWorkspace:** `/dictator` (dictator or scorer), `/team-builder` (captain or dictator), `/editor` (editor or dictator).
- **AdminDashboard:** a dictator sees every tab except the retired "Captains" tab; a scorer sees **Live Matches only**.
- **LiveController (scorer):** "No matches assigned to you in this division" as its empty state.
- **Access Control:**
  - one checkbox per role per account;
  - your own and the last dictator grant are refused with the server message;
  - a hint when a captain or scorer grant has no active assignment left (for example all its seasons have ended), with Revoke.
- **New `ManageScorers.jsx`:**
  - lists assignments, each with Revoke;
  - the Assign form takes an account, a division and season, an optional match and an optional expiry;
  - it warns when the scorer captains a team in that match.
- **Teams & Rosters:** a captain panel per entry (assign, change, revoke) that shows a 409 clash clearly.
- **TeamBuilder:**
  - sourced from `captain_assignments`, and shows `teams.name`;
  - a selector when a captain holds several assignments;
  - a "Team details" form.
- **Delete `ManageRegistrations.jsx`.**
- **States:** every new view handles loading, empty, success and error.

## Rollback
- **Migration A is forward-only.** The old app breaks on the new `user_roles` shape, so commits 1–5 ship together. A defect is fixed by a forward migration (SL-004 §5).

- **UI-only commits** revert cleanly.
