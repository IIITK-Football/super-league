# Plan: reduce the current backend's latency before the Workers migration

Status: diagnosis and plan only. The item cannot start until the phase gate opens. No application code, migration or setting has been changed. Every measurement below was taken against this repository's local Supabase only (API 127.0.0.1:54321, database 127.0.0.1:54322, seeded data, 2026-11-18). Each statement is labelled **[local]** (measured here), **[owner]** (needs the owner's staging measurement), or **[inference]** (reasoning that the owner's measurement must confirm).

## Issue
`GET /api/home/dashboard?division=wsl` on the develop Vercel Preview took 11.24 s, 6.72 s and 5.00 s across three consecutive manual requests. The first request pays an extra penalty, but the warm requests are still slow. The same route answers in about 25 ms against local Supabase. So the cost is not compute or query execution. It is the number of sequential network round trips the route makes, multiplied by the per-trip latency on the hosted path.

Before the Workers migration (SL-030), this item must:
- record a repeatable staging baseline (cold and warm);
- set a numeric warm target;
- make a focused optimization on the existing Next.js route that preserves its response and authorization behavior;
- recommend the minimum sufficient Worker topology for D-05.

## Evidence

### 1. Owner's preliminary sample [owner]
- Develop Vercel Preview, `GET /api/home/dashboard?division=wsl`, three consecutive requests: 11.24 s, 6.72 s, 5.00 s.
- The sample did not record function region, status, headers or the client's location. It cannot separate function startup from network or database time. The repeatable method in Scope replaces it.

### 2. What the route does (`backend/app/api/home/dashboard/route.ts`, `backend/lib/scope.ts`)
- The client is created at module scope with the publishable key, so warm invocations can reuse it. `revalidate = 0`, so nothing is cached.
- Every query below is awaited one after another. There is no `Promise.all`. That makes **11 strictly sequential PostgREST requests** for a season with fantasy leaders, and 9 when the fantasy RPC returns nobody:

| # | Query | Depends on | Rows / payload, wsl 2026 [local] | p50 [local] |
|---|-------|-----------|-----------------------------------|-------------|
| 1 | `divisions` by slug (`resolveScope`) | — | 1 / 71 B | 1.8 ms |
| 2 | `seasons` current for the division (`resolveScope`) | 1 | 1 / 111 B | 1.9 ms |
| 3 | `newsletter select('*')` top 5 by date | — (not season-scoped) | 5 / 3.5 KB | 1.7 ms |
| 4 | `season_player_stats` top scorer | 2 | 1 / 110 B | 4.1 ms |
| 5 | `season_player_stats` top assister | 2 | 1 / 110 B | 3.9 ms |
| 6 | `team_entries` team ids (`seasonTeamIds`) | 2 | 8 / 409 B | 1.7 ms |
| 7 | `teams in (…)` | 6 | 8 / 3.7 KB | 1.8 ms |
| 8 | `matches` + home/away names + **all goals of all season matches with player names** | 2 | 56 / **47.8 KB** | 5.1 ms |
| 9 | `rpc season_fantasy_leaderboard(p_limit 5)` | 2 | 4 / 353 B | 1.7 ms |
| 10 | `user_profiles in (…)` nicknames | 9 | 4 / 264 B | 1.5 ms |
| 11 | `division_flairs in (…)` | 9 | 0–5 / ~0 B | 1.5 ms |

- There is no N+1 loop: every list lookup is one `in (…)` query.
- **The dependency graph only needs 3 sequential rounds** (scope; season reads; RPC follow-ups). The route uses 11.
- **Over-fetching:**
  - Query 8 embeds every goal of every match in the season, with scorer names (47.8 KB, 50.1 KB uncompressed through raw REST). Only the goals of the single hero match (live, or else the next scheduled) are used. Without the goals embed the same matches query is **18.2 KB** [local].
  - Query 3 selects `*`, including the full article `content`. The home page (`NewsArticle.jsx`) renders only `id`, `title` and `image_url`. Locally the five rows are 3.5 KB; on hosted data the size depends on the article bodies [owner].
  - Query 7 locally carries inline SVG data-URI logos from the seed (about 450 B each). Hosted rows hold URLs.
- **Whole-table reads:** see section 4 (`season_player_stats`).

### 3. Local route timings [local]
Method: a throwaway vitest harness in the session scratchpad (not tracked) calls the real `GET` handler, as `season-scoped-routes.integration.test.ts` does, with `next/headers` mocked. It ran 1 first call followed by 20 warm calls per division.

| Division | First call | Warm p50 | Warm p90 | Max | Status | Body |
|---------|-----------|----------|----------|-----|--------|------|
| wsl | 85 ms (incl. first connections) | 23.4 ms | 34.1 ms | 38.4 ms | 200 | 7.2 KB |
| super-league | 32 ms | 28.0 ms | 31.3 ms | 35.0 ms | 200 | 7.1 KB |

- The sum of the per-query p50s is 26.8 ms (wsl) and 24.8 ms (super-league), which equals the route time. The route is entirely round-trip bound. JavaScript work (standings and form for 56 matches) is negligible.
- Route module import (cold module load) took 51 ms.

### 4. Query plans [local]
All plans were run as role `anon` inside a rolled-back transaction, on PostgreSQL 17.

- **`season_player_stats`** (security-invoker view, queries 4 and 5):
  - The `season_id` filter is **not pushed down**. The `listed` and `lines` CTEs are planned as materialized. Each call:
    - seq-scans all `matches` (168 rows) and expands every `scorers`/`assists` JSON array (804 elements);
    - seq-scans all `goals` twice (446 + 358 rows);
    - aggregates 633 (match, player) pairs and 185 season lines across **every season**;
    - only then filters to the one season (59 rows).
  - Each call costs 3.7–4.2 ms execution plus 1.9–2.3 ms planning. The route does this twice per request.
  - A season-first rewrite of the same logic (filter `matches` by `season_id` first, then join goals and the JSON) runs in 1.3–1.8 ms execution and 1.1–1.2 ms planning.
  - Cost today is a few milliseconds. It grows linearly with the number of seasons and goals ever recorded, because each request re-aggregates history.
- **`season_fantasy_leaderboard`** (SECURITY DEFINER, `row_security off`): 1.3 ms. Its seq scan of `predictions` (672 rows) is not a problem at this size.
- **Goals for one season's matches:** hash join with a seq scan of `goals` (446 rows), 0.1 ms. `goals` has **no index on `match_id`**, and `predictions` has none on `match_id`. Neither index is justified by the local plans: both scans cost under 1 ms. Add one only if a staging plan shows real cost.

### 5. Simulated network latency [local]
- Method: the harness wrapped `fetch` to add a fixed delay before each PostgREST request, standing in for function-to-database round-trip time.
- It compared the current route with a **scratch prototype** of the restructured route (`Promise.all` rounds, goals only for the hero match, team names via a `team_entries → teams` embed).
- The prototype's JSON **deep-equals** the current route's output for `wsl`, `super-league` and `freshers` (with and without `season=2026`), and returns the same 404/400 statuses for `mens` and a malformed slug.

| Added RTT per request | Current route p50 | Prototype p50 (4 sequential rounds) |
|-----------------------|-------------------|--------------------------------------|
| 0 ms | 25 ms | 12 ms |
| 25 ms | 398 ms | 151 ms |
| 100 ms | 1 221 ms | 446 ms |
| 200 ms | 2 356 ms | 855 ms |

- The current route costs about 11.5 × RTT. The prototype costs about 4 × RTT.
- Folding the two `resolveScope` lookups into one request gives 3 rounds, about 3 × RTT, a ~73 % reduction of the network-bound time at any RTT.

### 6. Identified contributors (ranked)
1. **11 sequential round trips** where 3 suffice [local, measured]. This is the dominant, structural cost, and it multiplies whatever the hosted RTT is.
2. **Per-request RTT on the hosted path** [inference; owner to confirm]:
   - `backend/vercel.json` does not exist and nothing sets a function region, so Vercel functions run in their default region (`iad1`, US East) unless the project settings say otherwise.
   - If the staging Supabase project is in another region (for example, near the users in India), each round trip crosses continents (150–250 ms or more).
   - 11 × that already explains 2–3 s. The observed 5 s warm suggests ~450 ms per sequential step, or extra client-to-function distance.
   - The `x-vercel-id` response header (`<edge POP>::<function region>::…`) and the Supabase project's region confirm this without changing any setting.
3. **First-request penalty** (11.24 s vs 6.72 s) [owner]:
   - Function cold start plus new TLS connections to Supabase on the first queries.
   - Parallelizing opens several connections at once on a cold instance. Warm instances reuse keep-alive connections.
4. **Over-fetching** [local]: 47.8 KB of season goals and the full article bodies on every request. This is secondary on fast links but adds transfer and JSON parse time.
5. **`season_player_stats` aggregates all history twice per request** [local plan]. This is milliseconds today and grows with history. SL-022 owns this view's internals.
6. **Frontend amplification** [local, out of scope]: `frontend/src/pages/Home.jsx` forces a full document reload on every PUSH/REPLACE navigation to the home page, so each navigation repeats the cold-ish page load and this request. Phase 9 should address this; it is recorded here only as context.

### A. Focused optimization of `/api/home/dashboard` (existing Next.js backend)
1. **Collapse the 11 sequential requests into 3 rounds**, with the same queries and RLS context (publishable key, no service role):
   - **Round A**, in parallel:
     - `resolveScope`, made a single request: `seasons` with `division:divisions!inner(id, slug, name)` filtered by division slug and current/slug/id. When no row comes back, the existing second lookup runs on that miss path only, so the 404 messages ("Division … not found" vs "… has no current season" vs "Season … not found in …") and the 400 validation stay exactly as they are.
     - The newsletter query.
   - **Round B**, `Promise.all`:
     - top scorer and top assister from `season_player_stats`;
     - teams through one `team_entries.select('team:teams(id, name, logo_url)')` (replaces queries 6–7);
     - matches **without** the goals embed;
     - the fantasy RPC.
   - **Round C**, `Promise.all`:
     - goals (with scorer names) for the hero match only;
     - `user_profiles` nicknames;
     - `division_flairs`.
   - Errors keep surfacing through `handleError` as today. `resolveScope` errors keep their status codes. The current route ignores errors on the other queries; that behavior is kept, not widened.
2. **Narrow selects:**
   - newsletter: `id, title, summary, date, author, image_url, category`, which drops `content`. Before narrowing, confirm with a grep that no consumer of `data.news` reads `content`. Today only `NewsArticle.jsx` reads it, using `id`, `title` and `image_url`.
   - matches: no goals embed.
3. **Add a `Server-Timing` response header** (`scope;dur=…, season;dur=…, fantasy;dur=…, total;dur=…`). It lets the owner's measurement separate server and database time from client network time, with no new dependency. It must not expose any data.
4. **Not in scope:**
   - any change to `season_player_stats` (SL-022 is told: push the season filter into the `matches` scan, measured 3.7–4.2 → 1.3–1.8 ms execution locally);
   - new indexes (no plan justifies one locally; reconsider only if a staging plan shows `goals.match_id` or `predictions.match_id` scans costing real time);
   - response caching (it would change freshness for live matches);
   - frontend changes.
5. **Optional, owner's decision (setting, not code):** if the baseline shows the Vercel function region differs from the Supabase staging region, co-locating them is the largest single remaining lever. It is a Vercel project setting and therefore needs the owner's explicit approval. The plan neither assumes nor performs it.

Expected effect [inference from section 5]: the route's network-bound time drops from ~11.5 × RTT to ~3 × RTT, about 70 % less at any hosted RTT. The payload the function receives drops by ~30 KB per request.

- **Deployment Protection:** if the Preview requires a bypass, the owner supplies it from their own environment. It is never written into the plan, evidence or shell history.
- **Cold:** the first request after a fresh Preview deployment, or after ≥ 30 minutes without traffic. Take 3 cold samples at different times and report each one.
- **Warm:** immediately after a cold sample, 30 sequential requests at about 1 per second. Report p50, p90 and max of `time_total`, plus `time_starttransfer` (TTFB), and confirm every status is 200.
- **Example** (owner's shell, `PREVIEW` set to the Preview origin):
  ```sh
  for i in $(seq 0 30); do
    curl -s -o /dev/null -D - "$PREVIEW/api/home/dashboard?division=wsl" \
  ```

  Line 0 is the cold sample; lines 1–30 are the warm series.

- **Correctness:**
  - Save one warm response body before and one after the optimization.
  - Compare them, ignoring the volatile live-match `minute`: `scope`, `standings`, `topScorer`, `topAssist`, `fantasyTop`, `news` (ids and titles) and `liveMatch` teams and scorers must match.

  - the follow-up with the same method (C2). The owner attests both with `pnpm work attest`.

### C. Warm-latency target (proposed; confirmed once the baseline is recorded)
- **Warm p50 ≤ 1.5 s and warm p90 ≤ 2.5 s** for `GET /api/home/dashboard?division=wsl` on the develop Preview with staging data, measured as above, with every response 200 and season-scoped.
- **Reasoning:**
  - The preliminary warm samples are 5.0–6.7 s, which implies ~450–600 ms per sequential step.
  - Going from 11 to 3 rounds should cut the network-bound part by ~70 % (section 5). That predicts roughly 1.4–1.9 s if per-step latency stays the same, so p50 ≤ 1.5 s is demanding but reachable without changing any setting.
  - If the owner's baseline shows a lower per-step latency (for example a 2.5 s warm p50), the target becomes **warm p50 ≤ 40 % of the baseline warm p50**, whichever of the two bounds is lower. This is recorded alongside the baseline before the optimization lands.
- **Cold latency** is recorded but has no target. It is dominated by function startup, which the Workers migration changes anyway.
- **Stretch (not required):** with the function region co-located with Supabase (owner's setting), warm p50 ≤ 0.6 s.

### D. Architecture assessment for D-05 / SL-030
**Route inventory** [local]: 54 `route.ts` handlers under `backend/app/api`.

| Domain | Routes | Notes |
|--------|--------|-------|
| World Cup fantasy (`wc/*`) | 26 (48 %) | Separate product. Grading and sync jobs call an external API. `wc/test` is a test route. |
| Division public reads | 9 | `home/dashboard`, `standings`, `schedule`, `leaderboard`, `legends`, `teams`, `teams/[team_id]/matches`, `players`, `players/[player_id]` |
| Match, team and roster management (scorer, captain, dictator) | 8 | `admin/matches`, `admin/matches/live`, `matches/update`, `admin/teams`, `admin/team-registrations`, `admin/freshers/player-image`, `admin/stats`, `captain/team-branding` |
| Predictions (division fantasy) | 6 | 4 user routes + `admin/predictions/grade`, `regrade-all` |
| Newsletter | 3 | `news`, `admin/newsletter`, `admin/newsletter/upload-url` (R2 presign) |
| Auth | 1 | `auth/login` |
| Media | 1 | `media/[...path]` (R2 proxy) |

All 54 share one database, one Auth system, one role model (SL-003), one owner and one deploy cadence. 20 of them use the cookie-based server client.

**Option 1 — one modular Hono Worker:**
- Domain modules are mounted with `app.route('/api/<domain>', …)`, with shared middleware for auth, scope resolution, errors and observability.
- It is served same-origin with the Pages frontend (a route on the same hostname), so there is no browser CORS policy.
- Pros:
  - one deploy and one set of bindings and secrets;
  - no inter-service hop;
  - one place for the authorization rules;
  - simplest local `wrangler dev`;
  - the smallest maintenance cost for a single-owner project with student-league traffic (bursty around matches, low absolute volume).
- Cons:
  - one bundle and blast radius;
  - one deploy rolls out every domain (mitigated by grouped tests and the CI gate);
  - a CPU-heavy job shares the request isolate's limits.

**Option 2 — a gateway plus several independently deployed Workers** (for example gateway, division, predictions, management, World Cup, media):
- Pros: independent deploys and isolation per domain, and per-Worker secrets.
- Cons:
  - Each extra Worker multiplies config, environments, CI and observability. Service bindings avoid public hops, but every call still crosses an extra Worker invocation.
  - Shared code (scope, roles, Supabase client) must be versioned across packages.
  - Authorization is spread over several deployables.
  - No route group here has a different owner, release cadence, scaling profile or compliance boundary that would justify this today.

**Latency consideration for either option:**
- A Worker runs near the user, but the database is in one region.
- Every sequential Supabase round trip then goes from the edge location to the database region. The round-trip reduction in Scope A therefore matters even more after the migration.
- SL-030 should evaluate Smart Placement (or an explicit placement near the Supabase region) for the API Worker.

**Recommendation (minimum sufficient topology): one modular Hono Worker**, same-origin with the Pages app, with internal domain modules matching the table above and World Cup as its own isolated module.
- Defer splitting. Record these explicit split triggers in D-05:
  1. a domain needs a different deploy cadence or owner;
  2. a scheduled or CPU-heavy job (World Cup sync and grading, prediction regrade) exceeds the request Worker's limits; in that case first move it to a Cron Trigger or Queue consumer of the same project, then to a separate Worker only if needed;
  3. a secret, such as the service role or private R2 credentials, needs a smaller blast radius than a module boundary gives;
  4. measured traffic isolation is required.
- World Cup is the first candidate if a trigger fires.
- A separate gateway Worker is unnecessary while there is only one service.

## Rollback
- The optimization is a single-route code change plus tests, with no migration, no data change and no setting change. Rollback is a revert of that one commit on `develop`, followed by the normal push. The previous behavior returns on the next Preview deployment.
- The `Server-Timing` header is additive and removable in the same way.
- If the owner later co-locates the Vercel function region (Scope A.5), that is an independent setting with its own revert. It is not part of this change.
- No index or view is changed. If a staging plan later justifies an index, it goes in its own forward migration, and dropping it is non-destructive.
