## Historical evidence from the pre-Worker plan

The figures, code shapes and inferences in this section document the prior Next/Vercel investigation. They are retained as evidence for that implementation and need fresh verification for the Worker.

### 1. Owner's preliminary sample [owner]
- Develop Vercel Preview, `GET /api/home/dashboard?division=wsl`, three consecutive requests: 11.24 s, 6.72 s, 5.00 s.
- The sample did not record function region, status, headers or the client's location. It cannot separate function startup from network or database time. The repeatable method in Scope replaces it.

### 2. What the route does (`backend/app/api/home/dashboard/route.ts`, `backend/lib/scope.ts`)
- The client is created at module scope with the publishable key, so warm invocations can reuse it. `revalidate = 0`, so nothing is cached.
- Every query below is awaited one after another. There is no `Promise.all`. That makes **11 strictly sequential PostgREST requests** for a season with fantasy leaders, and 9 when the fantasy RPC returns nobody:

| # | Query | Depends on | Rows / payload, wsl 2026 [local] | p50 [local] |
|---|-------|-----------|-----------------------------------|-------------|
| 1 | `divisions` by slug (`resolveScope`) | — | 1 / 71 B | 1.8 ms |
| 2 | `seasons` current for the division (`resolveScope`) | 1 | 1 / 111 B | 1.9 ms |
| 3 | `newsletter select('*')` top 5 by date | — (not season-scoped) | 5 / 3.5 KB | 1.7 ms |
| 4 | `season_player_stats` top scorer | 2 | 1 / 110 B | 4.1 ms |
| 5 | `season_player_stats` top assister | 2 | 1 / 110 B | 3.9 ms |
| 6 | `team_entries` team ids (`seasonTeamIds`) | 2 | 8 / 409 B | 1.7 ms |
| 7 | `teams in (…)` | 6 | 8 / 3.7 KB | 1.8 ms |
| 8 | `matches` + home/away names + **all goals of all season matches with player names** | 2 | 56 / **47.8 KB** | 5.1 ms |
| 9 | `rpc season_fantasy_leaderboard(p_limit 5)` | 2 | 4 / 353 B | 1.7 ms |
| 10 | `user_profiles in (…)` nicknames | 9 | 4 / 264 B | 1.5 ms |
| 11 | `division_flairs in (…)` | 9 | 0–5 / ~0 B | 1.5 ms |

- There is no N+1 loop: every list lookup is one `in (…)` query.
- **The dependency graph only needs 3 sequential rounds** (scope; season reads; RPC follow-ups). The route uses 11.
- **Over-fetching:**
  - Query 8 embeds every goal of every match in the season, with scorer names (47.8 KB, 50.1 KB uncompressed through raw REST). Only the goals of the single hero match (live, or else the next scheduled) are used. Without the goals embed the same matches query is **18.2 KB** [local].
  - Query 3 selects `*`, including the full article `content`. The home page (`NewsArticle.jsx`) renders only `id`, `title` and `image_url`. Locally the five rows are 3.5 KB; on hosted data the size depends on the article bodies [owner].
  - Query 7 locally carries inline SVG data-URI logos from the seed (about 450 B each). Hosted rows hold URLs.
- **Whole-table reads:** see section 4 (`season_player_stats`).

Method: a throwaway vitest harness in the session scratchpad (not tracked) calls the real `GET` handler, as `season-scoped-routes.integration.test.ts` does, with `next/headers` mocked. It ran 1 first call followed by 20 warm calls per division.

| Division | First call | Warm p50 | Warm p90 | Max | Status | Body |
|---------|-----------|----------|----------|-----|--------|------|
| wsl | 85 ms (incl. first connections) | 23.4 ms | 34.1 ms | 38.4 ms | 200 | 7.2 KB |
| super-league | 32 ms | 28.0 ms | 31.3 ms | 35.0 ms | 200 | 7.1 KB |

- The sum of the per-query p50s is 26.8 ms (wsl) and 24.8 ms (super-league), which equals the route time. The route is entirely round-trip bound. JavaScript work (standings and form for 56 matches) is negligible.
- Route module import (cold module load) took 51 ms.

### 4. Query plans [local]
All plans were run as role `anon` inside a rolled-back transaction, on PostgreSQL 17.

- **`season_player_stats`** (security-invoker view, queries 4 and 5):
  - The `season_id` filter is **not pushed down**. The `listed` and `lines` CTEs are planned as materialized. Each call:
    - seq-scans all `matches` (168 rows) and expands every `scorers`/`assists` JSON array (804 elements);
    - seq-scans all `goals` twice (446 + 358 rows);
    - aggregates 633 (match, player) pairs and 185 season lines across **every season**;
    - only then filters to the one season (59 rows).
  - Each call costs 3.7–4.2 ms execution plus 1.9–2.3 ms planning. The route does this twice per request.
  - A season-first rewrite of the same logic (filter `matches` by `season_id` first, then join goals and the JSON) runs in 1.3–1.8 ms execution and 1.1–1.2 ms planning.
  - Cost today is a few milliseconds. It grows linearly with the number of seasons and goals ever recorded, because each request re-aggregates history.
- **`season_fantasy_leaderboard`** (SECURITY DEFINER, `row_security off`): 1.3 ms. Its seq scan of `predictions` (672 rows) is not a problem at this size.
- **Goals for one season's matches:** hash join with a seq scan of `goals` (446 rows), 0.1 ms. `goals` has **no index on `match_id`**, and `predictions` has none on `match_id`. Neither index is justified by the local plans: both scans cost under 1 ms. Add one only if a staging plan shows real cost.

### 5. Simulated network latency [local]
- Method: the harness wrapped `fetch` to add a fixed delay before each PostgREST request, standing in for function-to-database round-trip time.
- It compared the current route with a **scratch prototype** of the restructured route (`Promise.all` rounds, goals only for the hero match, team names via a `team_entries → teams` embed).
- The prototype's JSON **deep-equals** the current route's output for `wsl`, `super-league` and `freshers` (with and without `season=2026`), and returns the same 404/400 statuses for `mens` and a malformed slug.

| Added RTT per request | Current route p50 | Prototype p50 (4 sequential rounds) |
|-----------------------|-------------------|--------------------------------------|
| 0 ms | 25 ms | 12 ms |
| 25 ms | 398 ms | 151 ms |
| 100 ms | 1 221 ms | 446 ms |
| 200 ms | 2 356 ms | 855 ms |

- The current route costs about 11.5 × RTT. The prototype costs about 4 × RTT.
- Folding the two `resolveScope` lookups into one request gives 3 rounds, about 3 × RTT, a ~73 % reduction of the network-bound time at any RTT.

### 6. Identified contributors (ranked)
1. **11 sequential round trips** where 3 suffice [local, measured]. This is the dominant, structural cost, and it multiplies whatever the hosted RTT is.
2. **Per-request RTT on the hosted path** [inference; owner to confirm]:
   - `backend/vercel.json` does not exist and nothing sets a function region, so Vercel functions run in their default region (`iad1`, US East) unless the project settings say otherwise.
   - If the staging Supabase project is in another region (for example, near the users in India), each round trip crosses continents (150–250 ms or more).
   - 11 × that already explains 2–3 s. The observed 5 s warm suggests ~450 ms per sequential step, or extra client-to-function distance.
   - The `x-vercel-id` response header (`<edge POP>::<function region>::…`) and the Supabase project's region confirm this without changing any setting.
3. **First-request penalty** (11.24 s vs 6.72 s) [owner]:
   - Function cold start plus new TLS connections to Supabase on the first queries.
   - Parallelizing opens several connections at once on a cold instance. Warm instances reuse keep-alive connections.
4. **Over-fetching** [local]: 47.8 KB of season goals and the full article bodies on every request. This is secondary on fast links but adds transfer and JSON parse time.
5. **`season_player_stats` aggregates all history twice per request** [local plan]. This is milliseconds today and grows with history. SL-022 owns this view's internals.
6. **Frontend amplification** [local, out of scope]: `frontend/src/pages/Home.jsx` forces a full document reload on every PUSH/REPLACE navigation to the home page, so each navigation repeats the cold-ish page load and this request. Phase 9 should address this; it is recorded here only as context.
