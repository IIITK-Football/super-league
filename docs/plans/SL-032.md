# Plan for SL-032 — Verify Worker parity for the active application flows

## Issue

SL-030 (runtime) and SL-031 (same-origin routing) established the Worker and proved its path. The [compatibility register](../contracts/worker-compatibility.md) lists the operations the product uses. The existing tests run handlers in Node and call some routes directly. Neither shows that each active contract group works for real people, through the deployed path, locally and on staging. The deployed path is browser → Pages → `API` binding → Worker → staging Data API. This item closes that gap for every active group. Two things are excluded:
- the World Cup archive's feature fidelity (D-02);
- HLS playback (SL-106).

## Evidence

- **Register:** 44 operations on 33 mounted paths, plus the screens' direct Data API dependencies ([register](../contracts/worker-compatibility.md)).
- **SL-030:** real Wrangler runtime, authorization, audit actor, atomic writes, and at most 3 Data API rounds per active read ([walkthrough](../walkthroughs/SL-030.md)).
- **SL-031:** same-origin routing, bearer forwarding, stable errors, `no-store`, and the release pair (`/version.json` plus `/api/health`), with a restored previous pair on staging ([walkthrough](../walkthroughs/SL-031.md), [rollback](../rollback/pages-worker-pair.md)).
- **Per-group integration tests** in `backend/tests/*` and `api/test/*` remain the CI safety net.
- **Reused tooling:**
  - `scripts/verify-local-routing.mjs`: local Pages and Worker processes, target guards;
  - `scripts/staging-routing-check.mjs` and `scripts/staging-media-check.mjs`: staging guards, Access headers, temporary staging accounts, PNG fixtures;
  - `scripts/ui-walkthrough/roles.mjs`: Playwright sign-in by session injection.

**Work:**
1. **API parity runner.** `scripts/parity/verify-parity.mjs --target local|staging`, with one module per group. It calls the site origin, so every request goes through the Pages function.
   - **Accounts and fixtures:** per run it creates tagged temporary accounts (dictator, editor, assigned captain, assigned and unassigned scorer, normal user, anonymous) and a tagged team entry, roster place and match. It deletes everything at the end.
   - **Per operation:** the allowed caller gets the expected status and the response keys the register lists as consumed. Each refused caller gets 401 or 403 with row counts unchanged. Writes are checked in the database (row and audit actor).
   - **Output:** one JSON evidence document. An active operation not exercised is reported as a gap, never a pass.
2. **Browser walkthrough.** `scripts/ui-walkthrough/parity.mjs`, using Playwright against the same targets; on staging it adds the Access headers. It drives each group's real screens to the stored result, with screenshots and a database or API check for each step.
3. **Fix failures** at their source, with a test in the owning group. Update the register with a status per group and links to the local and staging evidence.
4. **Record the rollback pair** and run the parity runner once against the previous pair (the owner rolls the Worker back; the old preview is used through its own URL).

**Hosted actions** (staging only, standing authorization):
- temporary tagged accounts and rows, created and deleted per run;
- uploads to the `sl-staging-*` buckets, cleaned up;
- the owner's Worker rollback and roll-forward.

Nothing touches production.

## Acceptance checks

- C1 (owner):
  - every active group passes the parity runner and the browser walkthrough, locally and on staging, including the current uploads;
  - every refused caller is refused, with nothing stored;
  - the previous release pair passes the parity runner;
  - the register names no unexplained gap;
  - archive feature bugs and HLS are recorded under D-02 and SL-106.

## Tests

- **Pure parts:** `backend/tests/tooling/parity-*.test.ts` covers the runner's verdicts, gap detection and target guards (tooling group).
- **Fixes:** each fix adds or changes a test in the group that owns the changed file. The strict check against `main` must pass.
- **Groups:** `pnpm test:group` for every affected group, then `pnpm work phase 3` at the phase boundary.

## Rollback

The runner and walkthrough only add tooling and evidence. Fixes found by them are ordinary changes, reverted by redeploying the previous compatible pair ([procedure](../rollback/pages-worker-pair.md)). No migration is planned. If a fix needs one, it is additive and is recorded with its own rollback note.
