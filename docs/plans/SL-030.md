## Bounded implementation sequence

1. **Establish the local target.** Coordinate with the checkout using the shared Supabase stack. Confirm `pnpm db:check` identifies project `backend` at `127.0.0.1:54322`. Start the Worker from the implementation checkout with `pnpm --dir api dev` and the local Data API at `127.0.0.1:54321`. Record the served commit, host, health output, a successful scoped public standings read, and that a local Worker configured with a non-local URL fails before outbound work. Test the rejected configuration with synthetic values and a stubbed outbound boundary.
2. **Verify identity, atomicity, and secrets.** Use local synthetic accounts and fixtures. Test a valid caller, missing, expired and tampered tokens, and verify unauthorized requests make no route data write. Verify a normal user cannot switch the current season and a captain cannot edit another team's player through the actual Worker or caller Data API entry point. Check unchanged rows for denials. Exercise a dictator RPC write and verify the actor recorded in `audit_log`, then induce a multi-write failure and confirm no partial state. Keep audit and authorization checks at the database boundary as well as the Worker where a route exists.
3. **Close the applicable D-04 transport gaps.** Map public, caller-token, and privileged clients and multi-write boundaries against [the accepted decision](../decisions/D-04-workers-supabase-access.md) and [its proof list](../decisions/D-04-workers-supabase-access-proposal.md). Inspect interactive elevated paths such as captain branding and grading before changing them. Preserve their access checks and audit actor. Keep any broader RPC rewrite in the owning parity slice unless required to resolve an SL-030 acceptance failure. Record unresolved policy discrepancies for an owner decision, with a concrete example and the affected acceptance check. Exercise the timeouts, retry only for idempotent reads as specified, verify bundle and browser credential isolation, and capture the dashboard round-trip count and safe `Server-Timing` output. Reuse SL-029 measurements when available. If the dashboard exceeds the accepted three rounds, record that check as open and use SL-029 for the focused optimization.
4. **Run the local checks and capture staging evidence.** Run `pnpm test:group api-services config` plus the owning role/audit groups when affected. Keep allowed and denied runtime results with the served SHA and commands. Once the authorized staging build is available, record its Worker build ID, SHA, Pages binding target, `/api/health` environment, scoped standings status/shape and response timings. Compare placements using the same endpoint and sample method only with owner-approved staging configuration. Keep placement changes only with measured improvement. Existing tests and deployed configuration can be reused as evidence when they prove the exact acceptance check.

## Owner actions and stop conditions

- The owner supplies or runs staging access, confirms the deployed environment and approved placement comparison, and attests the recorded staging check under the standard backlog workflow. Treat settings changes and hosted fixture writes as separate owner actions.
- Stop local execution on a wrong target, unavailable local stack, or conflicting checkout. Stop hosted verification on missing owner authorization, unconfirmed staging identity, or any indication of a production target.
- Leave the item open if a required check fails, D-04 discrepancies remain unresolved, or evidence or attestation is missing. Keep the existing frontend contract throughout. Rollback uses a prior compatible Worker and Pages release.
- Media implementation, full parity, runtime retirement, and general performance tuning stay with their Phase 3 items. The carousel failure remains open under SL-032.
