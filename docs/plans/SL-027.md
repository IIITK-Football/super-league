# Plan: append-only audit history for sensitive changes

## Issue
Sensitive changes had no durable record of who made them:
- division and season configuration;
- roles and captain assignments (team registrations);
- match scores and goals;
- players and season rosters.

Many of these are direct Data API writes, so logging in API routes alone would miss them.

## Evidence
- The dictator dashboard writes divisions, seasons, sections, team entries, players and roster places straight to the Data API (`ManageDivisions.jsx`, `ManageRosters.jsx`). Only RLS stands between the caller and the row, and nothing records the change.
- Roles are changed through `ManageRoles.jsx` (Data API); captain assignment and live scoring go through API routes.
- `players.player_private_details.email` is private contact data and must never be copied into a history.

## Scope
- **Migration `20261126000000_audit_history.sql`:**
  - `public.audit_log`: time; actor (`auth.uid()`, plus the request role, or the database session for server, seed and migration work); action; table; record id; and a safe summary.
    - An insert or delete stores the record's values.
    - An update stores only the changed fields, as from → to.
    - Private columns are stored as `[redacted]` or `{"changed": true}`.
    - Noise columns (`created_at`, `updated_at`, the running match clock) are ignored; an update touching only those is not recorded.
  - One `SECURITY DEFINER` trigger function, `audit_row_change(keys, private, noise)`. It is attached to `divisions`, `seasons`, `season_sections`, `section_types`, `team_entries`, `user_roles`, `team_registrations`, `matches`, `goals`, `players`, `roster_memberships` and `player_private_details`.
  - Append-only on every path: no write privilege for anon, signed-in users or the server key; a trigger refuses UPDATE, DELETE and TRUNCATE for every role, the owner included; RLS lets dictators read.
  - Later slices (SL-042 account links, SL-024 assignments, SL-022 events) attach the same function to their tables.
- **Dictator view.** An "Audit History" tab (dictator only, like Divisions & Seasons) lists the newest changes with actor email, action, table, record and summary. It has a table filter, a person filter and "show older changes" paging, and handles loading, empty and error states. It only reads.
- **Out of scope:** the full RLS audit (SL-025); audit of predictions grading, newsletter and flairs; retention policy.

## Acceptance checks
- C1: the history exists, has RLS, and its writer cannot be called directly.
- C2: a dictator's change through the Data API is recorded with that dictator as actor and a changed-fields-only summary; no-op updates and the match clock are not recorded; composite records are identified.
- C3: nobody can add, change or remove history, the server key and owner included; only dictators read it.
- C4: no private contact data appears in the history.
- C5: the Audit History view handles its states, filters and paging, and is offered to a dictator only.
- C6: through the real local Data API, a dictator finds their own change filtered by table and person; a normal user sees none.
- C7 (owner): the staging deploy applies the migration and the view works on staging.

## Rollback
The migration only adds objects. Reverting the UI commit removes the tab without touching data. If a trigger misbehaves, a forward migration drops that trigger. The history itself is kept, because it is append-only by design. The audited tables are unchanged, so dropping every trigger restores the previous behaviour exactly.
