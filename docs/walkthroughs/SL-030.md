## Summary

The API Worker now reaches Supabase the way D-04 decided, and the record shows it working through the real runtime, locally and on staging.

- Every client is built per request by `backend/lib/supabase/clients.ts`, through three factories: public, caller and job. Each Data API call has a timeout (8 s, or 20 s for jobs), retries once only for an idempotent read that failed on the network, and is counted into a `Server-Timing` header.
- Every active read takes at most three sequential Data API rounds. A test counts the rounds of every active GET route against the local stack.
- Writes a person starts no longer use the secret key, so the audit history names that person.
- A multi-write is one transaction.
- Expired tokens and database refusals get correct answers instead of 500.
- `/api/health` names the deployed commit and Worker version.
- Smart Placement was measured on staging. It did not help, so it is not kept.

- **Admin grading:** still writes with the secret key after a dictator check, which D-04 allows until an RPC replaces it.
- **Round latency:** each Data API round costs about 230 ms from the staging Worker.
- **Cold first request:** the first request after a deploy was slow before reaching the Worker (Access and the Pages Function). SL-029 and SL-031 own this.
- **Next-only routes:** `auth/login`, `legends` and `admin/teams` still build clients directly. The Worker does not serve them, and SL-034 retires them.

## Rollback

Redeploy the previous compatible Worker from `develop` history (for example the commit before `fdb78b3`). The `/api` contract did not change, so the deployed Pages site keeps working with either release.

The two migrations are additive functions. A forward migration can drop them only after `team-branding` and `admin/matches` stop calling them, so rolling back the code alone leaves the functions unused but harmless.
