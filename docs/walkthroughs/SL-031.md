## Summary

The browser reaches the API on its own origin, and this is now proven end to end, locally and on staging.

- A request to `/api/*` goes through the Pages function, then the `API` service binding, to the Worker.
- The caller's bearer token is forwarded: a signed-in read succeeds, and a protected write is refused by the database rather than for a missing session.
- Errors are stable JSON, and every `/api` answer is explicitly not cacheable (`Cache-Control: no-store`).
- The site names its release in `/version.json`, and the Worker names its own in `/api/health`.
- On staging, the previous site-and-Worker pair was restored and the same requests repeated, then staging was rolled forward again.

## Assumptions and deviations

- **Explicit no-store:** `/api` answers now default to `Cache-Control: no-store`, so the cache behaviour is explicit; before, there was no header.
- **Release identity:** `/version.json` was added so a site release can be named.
- **Preview rollback:** Pages preview deployments cannot be rolled back, so the restored site is the older deployment's own URL. The rollback restored the release before SL-031 (`--previous` mode) because SL-032 cannot start before SL-031 is done.
- **Stray processes:** while gathering evidence, a stray local Wrangler process from SL-030 shadowed the Worker in the local dev registry. It was stopped, and the guard Worker now uses its own name.

## Risks and follow-ups

- **Cold first request:** the slow first request after a deploy (Access and the Pages Function) is measured but not addressed here (SL-029).
- **Production pair:** the production site and Worker get the same checks at the release, via the release checklist (SL-101).
