# Walkthrough: SL-027 Append-only audit history for sensitive changes

Facts between the generated markers are written by `pnpm work done`; do not edit them. Fill in every other section.

## Summary

Sensitive changes now leave a permanent record of who changed what and when.
- **What is recorded:** every write to divisions, seasons, sections, team entries, roles, captain registrations, matches, goals, players, roster places and private player details. One database trigger records it, so direct Data API writes, RPCs and API routes are all covered.
- **What each entry holds:** the signed-in actor and only the fields that changed. Private contact data is never stored, and the match clock and no-op updates are not recorded.
- **Nobody can change or remove history:** not dictators, not the server key, not the database owner.
- **Viewing it:** dictators read it in a new Audit History tab with table and person filters and paging. Every person in the history is listed by their verified sign-in email, with their name as context, never a raw id or an editable profile email.

## Assumptions and deviations

- **Actor:** the authenticated user id from the request's JWT. Server-side writes record the database session role instead of a person.
- **Actor labels:** they come from the verified Auth email, not `user_profiles.email`, which users can edit themselves (owner decision 2026-11-19).
- **Test residue:** staging and local test runs leave synthetic history rows, because the history cannot be deleted. The tests tag them so they are recognisable.

## Risks and follow-ups

- **Growth:** the history grows with every reseed and test run on staging. That is acceptable for synthetic data.
- **Not covered yet:** tables added by later items (assignments, match events) must attach the trigger as they ship. SL-025's audit will check completeness.
- **Raw ids in entries:** an entry's record id (for example the account affected by a role change) can still show as an id. Labelling it needs a broader account lookup, planned with SL-025.

## Rollback

Forward-only. A follow-up migration can drop the triggers and the Audit History tab can be reverted without touching other data. The recorded history should be kept, not deleted.
