## Assignment

**Entry point.** Start with the storage calls, configured buckets, database references, and screenshot and backup jobs.

### Acceptance scenario

1. Reconcile every source object to an owner, key, reference, access policy and rollback path. Resolve unknown owners and collisions before copying.

**Disposition: not started.** [D-06](../../docs/decisions/D-06-domains-and-buckets.md) classifies storage purposes and [current upload code](../../backend/lib/storage.ts) documents some keys. The object inventory, ownership map, reviewed rename manifest and dry-run report remain. Include the existing `intro` playlists, referenced resources, and byte-range objects with their path relationships. For rollback, record which retained objects the prior Worker and Pages release reads.

**Issue:** R2 URLs and credentials are scattered, bucket purposes overlap, and the `backup` bucket contains sensitive backup artifacts that must not be treated as public application media.

**Required outcome:** Map every public URL, object key, upload/read path, CI job, poster, stream, and database image URL to a bucket and retention/access requirement. Classify backup, fresher-images, intro, news-images, player-images, playstyles, screenshot, and team-logos separately before renaming/reorganizing any bucket. Inventory current objects, identify opaque/random or client-filename-derived keys, identify each object's owning record and scope, and produce a complete old-key → target-bucket/key migration manifest before any bulk copy or upload. Account for the fact that a player identity and its FUT portrait are shared across roster places, while roster membership is division/season/team-specific: the canonical player portrait key is identity-scoped (`players/<player-id>.png`), not duplicated under season/team folders. Include a dry-run report for missing ownership, duplicate targets, and collisions; resolve these before copying.

**Completion checks:** Every current reference has a destination owner, access policy (public/private), object migration plan, and rollback path. Before copying/uploading, the reviewed plan identifies each source object, owner, current reference, target bucket/key, and collision outcome; it accounts for every existing object, including random names. Sensitive storage remains private and is never exposed as public application media.

**Usable in its own phase (rule R10):** not applicable (inventory).
