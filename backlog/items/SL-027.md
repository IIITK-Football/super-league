**Added (2026-11-18):** split out of SL-025 so that every later slice writes its sensitive changes to one history as it ships, instead of the audit being retrofitted at the end of Phase 2.

**Issue:** Sensitive changes have no durable record of who made them:
- division and season configuration (SL-020), written directly through the Data API;
- roles, captain and scorer assignments;
- account-to-player links, registrations, match scores and events.

Several of these paths are direct Data API writes, so API-level logging alone would miss them.

**Required outcome:**
- Add an append-only audit history recording actor (`auth.uid()` or the service identity), action, target table and id, time, and a safe before/after summary. Secrets and private contact data are never logged.
- Capture changes in the database (triggers on the audited tables), so direct Data API, RPC and API writes are all recorded. Attach it now to the SL-020 configuration tables; SL-042, SL-024 and SL-022 attach it to their tables as they ship.
- Nobody, including the actor and dictators, can update or delete audit rows through the Data API. Only dictators can read them.

**Completion checks:**
- A configuration change made through the Data API by a dictator is recorded with the right actor.
- Audit rows cannot be updated or deleted by any role.
- Non-dictators cannot read the history.
- No secret or private contact field appears in a summary.
- The migration applies to a reset local database and on staging.

**Usable in its own phase (rule R10):** this item is not complete until a dictator reads the recent audit history (filter by table and actor) in a minimal dictator dashboard view. The flow follows the current frontend patterns (no redesign), handles loading, empty, success and error states, and is verified through the real UI, API and database path (allowed and denied cases) locally and on staging.
