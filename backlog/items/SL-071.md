**Issue:** Per-route R2 clients and hard-coded public URLs make local testing and future provider changes fragile.

**Required outcome:** Define one server-side storage interface for upload, signed upload, read/public URL, and object metadata. Rewire every backend upload, replacement, read, and delete route/helper to use this interface; no route may construct an independent R2 client or upload directly outside it. Provide separate bucket binding/config values for `backup`, `fresher-images`, `intro`, `news-images`, `player-images`, `playstyles`, `screenshot`, and `team-logos`. Provide a separate public base URL for each bucket that is intentionally public. Define one upload-key policy: the server generates stable, useful keys from validated entity IDs/slugs and media purpose; client filenames are metadata only and never become storage paths. Use predictable purpose-specific prefixes. A player's shared portrait uses the identity-scoped key `players/<player-id>.png`, independent of division, season, or team; roster scope remains database metadata and must not create competing portrait copies. Apply equivalent stable ID-based keys to every other upload flow. Before copying or uploading existing assets, document the target bucket and exact key format for every media purpose, produce the source-to-target rename manifest, and run a dry-run collision/missing-owner report. Keep the backup bucket private and server-only even if it needs its own endpoint/binding value; never expose its URL or credentials through a browser variable.

**Completion checks:** Every backend upload/read/delete path uses the shared storage interface; each media purpose resolves to one configured bucket; missing settings fail clearly; local, develop, and production configuration are isolated. Upload tests prove arbitrary client filenames cannot control keys, generated keys follow the documented stable naming scheme, and upload/replace/delete flows resolve the correct object for its owner and scope.

**Moved (2026-11-18):** all R2 work now runs in Phase 3, after the Worker runtime (SL-030), so that Phases 4–6 consume the finished storage system instead of redoing its migration (owner decision 2026-11-18). Later features (portraits, share images, home video, rules images) use only this interface.

**Usable in its own phase (rule R10):** not applicable (storage infrastructure). Existing uploads and media reads keep working through it.
