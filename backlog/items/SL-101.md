## Assignment

**Entry point.** Use the release checklist for each slice, then repeat it for the final cutover.

### Acceptance scenario

1. Record staging and production dates separately, verify counts, migration rehearsal, owner approvals, recovery proof and seed separation.

**Restated (2026-11-20, owner):** production already received the Phase 2 schema (2026-11-19), and the owner decided on one production release per slice. This item is therefore a per-release checklist that every slice follows, plus the final cutover.

**Issue:** Local correctness does not prove a safe production transition. The app has historical teams, players, match events, predictions, and media URLs that must retain integrity. Staging holds only the synthetic seed, so only a production-shaped clone can show anomalies in real data.

**Required outcome:**
- **Per release:** (1) the slice's local and staging checks pass; (2) its migration is rehearsed on the isolated production-shaped clone (restored from a verified backup, ports 563xx only), with the counts, totals and role reports reviewed by the owner; (3) the release pull request is merged with a merge commit; (4) the workflow's verified pre-migration backup is confirmed and the owner approves `Database Production`; (5) read-only post-release checks. Nothing is written to the backup source, staging or production during a rehearsal.
- **Final cutover:** reconcile counts and key relationships across the whole history, validate role mapping, verify images and media after the bucket moves, rehearse rollback, and obtain the owner's review before the API cutover.

**Completion checks:** Counts and referential checks pass at each release and at the end; seeded fixtures remain local-only; each production migration is forward-only or has an approved rollback strategy; required data-retention artifacts remain intact and access-controlled; every release has its checklist recorded in `docs/release.md`.
