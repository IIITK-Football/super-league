**Issue:** A manual timing sample of `GET /api/home/dashboard?division=wsl` on the develop Vercel Preview returned 11.24s, 6.72s, and 5.00s across three consecutive requests. This suggests a first-request penalty, but the warm responses remain slow. The sample is preliminary and does not by itself distinguish function startup from database, network, or route work.

**Required outcome:** Before beginning the Workers migration, measure and reduce the current backend's warm latency on staging. Use the same representative API route, staging data, and measurement method for the baseline and follow-up. Record the conditions, cold result, repeated warm results, response status, and a numeric warm-latency target in `docs/plans/SL-029.md`. Diagnose the endpoint's contributing work and make a focused optimization on the existing backend before porting it. Preserve response behavior and verify the actual route against local Supabase and staging.

As part of this pre-migration assessment, compare a simple modular Hono Worker with a gateway and multiple independently deployed Workers. Base the recommendation on the actual route boundaries, operational needs, expected traffic, latency, and maintenance cost. Record the minimum sufficient topology for SL-030 and the existing D-05 decision; do not assume microservices are required.

**Completion checks:**
- A repeatable staging baseline distinguishes the first request from subsequent warm requests for the dashboard API (and records any additional representative route used).
- The chosen numeric warm-latency target is met after the focused optimization, with the route returning the expected season-scoped data.
- Existing route and authorization tests pass locally; the optimized route is verified against staging before the Workers migration begins.
- The architecture assessment recommends a justified minimum Worker topology and informs D-05 / SL-030.
- No Production endpoint or data is used for diagnosis or verification.

**Ordering:** SL-030 depends on SL-029. Complete this latency work and architecture assessment before establishing the Worker runtime or porting backend routes.

**Usable in its own phase (rule R10):** not applicable; this is backend performance and architecture work that preserves an existing user flow.
