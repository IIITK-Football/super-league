**Issue:** Existing established teams and Freshers' registration/team-member path have different structures and management flows.

**Required outcome:** Bring existing team management and Freshers' registration/team builder into one model while preserving useful team registration and captain workflows. Captains may submit team details and, where enabled, lineups using players already created by a dictator. Only dictators may create, remove, rename, or otherwise manage player records. Scope captain access to their assigned team and season; allow dictator assignment/override and configurable registration requirements.

**Completion checks:** All divisions can use registration, team details, team branding, and captain assignment; player record changes are dictator-only; legacy Freshers-only tables are no longer runtime dependencies; existing data maps without losing people or team history.

**Usable in its own phase (rule R10):** this item is not complete until captains manage their team details and branding, and dictators assign captains and manage team entries for a season, from the existing captain and dictator surfaces. The flow follows the current frontend patterns (no redesign), exposes the real authorized action, handles loading, empty, success and error states, and is verified through the real UI, API and database path (allowed and denied cases) locally and on staging. Phase 9 only consolidates and refines it.

**Dictator team-entry workflow (owner request 2026-11-19, assigned here from SL-020):** the dictator dashboard must offer:
- dependent **division → season → team entry** selectors, listing only the entries of the chosen division and season;
- adding an existing or new team to the selected season (a `team_entries` row). Team identity and branding (name, logo, colour) stay division-wide; participation and roster are per season (`team_entries`, `players.team_entry_id`, `team_registrations.season_id`). The SL-020 schema already holds all of this, so no migration is expected for the selectors;
- a team's players shown only after that team is selected, with a player chosen from a dropdown before editing. Player identity fields and account links belong to SL-042, and player creation is currently broken there (see SL-042);
- a captain change that updates the existing registration or entry.

**Defect to fix here: changing a captain fails with `duplicate key value violates unique constraint "team_registrations_pkey"`.**
- *Cause:* `backend/app/api/admin/team-registrations/route.ts` saves with `upsert({ id: body.id, …, captain_id }, { onConflict: 'captain_id' })`. The table has two unique keys, `team_registrations_pkey (id)` and `team_registrations_captain_id_key (captain_id)`. When `ManageRegistrations.jsx` saves an existing registration with a different captain, it sends the existing `id` and a new `captain_id`. `INSERT … ON CONFLICT (captain_id)` arbitrates only on `captain_id`, finds no conflict, and inserts a second row with the existing `id`, which the primary key rejects.
- *Not caused by SL-020:* the same upsert existed before SL-020 (commit `025213f`), which only replaced `division` with `season_id`.
- *Reproduce:* open Teams & Rosters, change the captain of an existing team and save.
- *Fix:* update the existing registration by `id` when it exists (insert only for a new team). Refuse, with a clear 409, a new captain who already captains another registration. Decide deliberately what happens to the previous captain's role (no role implies another).
- *Acceptance:* changing a captain to someone else and back keeps one registration with its roster and season. A denied case covers a captain already assigned elsewhere. Verified through the real UI, API and database path, locally and on staging.
