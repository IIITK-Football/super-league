**Consolidated (2026-11-18):** this slice takes the captain-assignment, team-details and registration-retirement parts of SL-041, including its captain-change defect. Scorer invitations and the phone workspace stay in SL-050. The broader RLS audit is SL-025.

**Issue:**
- `admin` acts as scorer in labels but receives broad management permissions, and `editor` is a legacy role.
- Captain assignment is `team_registrations.captain_id`, which is unique per captain across all seasons and is a Freshers-only structure.
- Captain branding and the team builder find a captain's team through that registration.
- Direct database policies are broader than the capability boundaries.
- Changing a captain fails (defect below).

**Required outcome:**
- **Roles:** use only the five roles. Resolve D-03 (multiple roles, assignment scope).
  - Remove the `admin` alias through a reviewed migration: `editor` stays the newsletter-only editor; `admin` becomes user unless a reviewed per-person assignment is recorded before the migration (SL-004 §3a).
  - Each role's API checks, RLS and UI decisions agree.
- **Captain assignment:** a scoped assignment to a team entry (season-specific), held together with the captain role (SL-003: both are required).
  - Port every caller of `team_registrations` (team builder, captain team-branding route, `ManageRegistrations`, the admin team-registration route, roster RPCs from SL-021, staging checks, seed) onto the assignment.
  - Then retire `team_registrations` behind guards that keep every captain and team.
- **Scorer assignment:** scoped to a season or match. Scorers reach the existing live-scoring tab with match-only powers. Legacy `admin` loses the broad dashboard.
- **Captain team details and branding:** name, short name, logo and colours, for the assigned team in every division.
- **Dictator controls:** assign and revoke roles and assignments. Every change is recorded in the SL-027 history.

**Completion checks:**
- Database policies, API checks and UI capability decisions agree.
- A normal account cannot write match data.
- A captain cannot create, remove, rename or otherwise manage player records.
- A scorer can operate assigned match fields but cannot change division configuration, role assignments, news, roster administration or predictions grading.
- A dictator can manage everything.
- No runtime reader of `team_registrations` remains, and the table is dropped with every assignment kept.

**Usable in its own phase (rule R10):** this item is not complete until all of the following work in the existing frontend:
- a dictator assigns and revokes roles and captain/scorer assignments from the dictator dashboard;
- a captain edits their team details and branding;
- an assigned scorer uses the live-scoring tab without dictator access.

The flow follows the current frontend patterns (no redesign), exposes the real authorized action, handles loading, empty, success and error states, and is verified through the real UI, API and database path (allowed and denied cases) locally and on staging.

**Defect to fix here (moved from SL-041): changing a captain fails with `duplicate key value violates unique constraint "team_registrations_pkey"`.**
- *Cause:* `backend/app/api/admin/team-registrations/route.ts` saves with `upsert({ id: body.id, …, captain_id }, { onConflict: 'captain_id' })`.
  - The table has two unique keys: `team_registrations_pkey (id)` and `team_registrations_captain_id_key (captain_id)`.
  - When `ManageRegistrations.jsx` saves an existing registration with a different captain, it sends the existing `id` and a new `captain_id`.
  - `INSERT … ON CONFLICT (captain_id)` arbitrates only on `captain_id`, finds no conflict, and inserts a second row with the existing `id`, which the primary key rejects.
- *Not caused by SL-020:* the same upsert existed before SL-020 (commit `025213f`).
- *Reproduce:* open Teams & Rosters, change the captain of an existing team and save.
- *Fix:* the captain assignment replaces the registration upsert. Changing a captain updates the existing assignment, and a captain already assigned elsewhere in the same season is refused with a clear 409. Decide deliberately what happens to the previous captain's role (no role implies another).
- *Acceptance:* changing a captain to someone else and back keeps one assignment with its roster and season. A denied case covers a captain already assigned elsewhere. Verified through the real UI, API and database path, locally and on staging.
