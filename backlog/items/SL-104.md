**Placement (2026-11-20, revised plan rev 5):** part of the first staging release candidate, the slice that also holds the Worker platform and port (phase 3). It is small and database-first (one RPC plus the existing profile card), so it builds directly on the target architecture with no Next-only code. If the 10-day candidate is at risk, this is the first item to move after it, without changing its scope.

**Issue:** since SL-042 a linked player can change only their portrait and preferred foot (`update_my_player(p_image_url, p_preferred_foot)`). Everything else on their card is edited by a captain or a dictator, so a player cannot keep their own public profile current.

**Required outcome:**
- **Player-editable (own linked player only):**
  - a **display name**, stored separately from the identity's first and last name. Roll number, email, legal name and the account link stay protected; the display name is shown wherever the player's name appears publicly, with the identity name as the fallback;
  - **FUT card details:** portrait, overall rating, attributes (the canonical `players.attributes.stats` shape, each value 1–99), preferred foot and play style (one catalog value or none). The database checks (`players_attributes_canonical`, the play-style catalog) apply unchanged.
- **Not player-editable:** team, season, roster place, jersey number and position stay under the existing team-management rules (captain within a writable assignment, dictator). The player path refuses them, and no team-management power is granted to the player.
- **One write path:** extend `update_my_player` (or replace it with one RPC taking only the permitted fields). It acts on the caller's own linked player only (`players.user_id = auth.uid()`). Every change is recorded in the audit history (SL-027), with the player as actor.
- **Shared fields:** rating, attributes and play style stay editable by the player's captain and by dictators as today. The latest write wins, every write is audited, and a dictator can correct any value.
- **Portrait upload** goes through the Worker's storage path, to staging buckets only outside production, with the server-generated key `players/<player-id>.png`.
- **Usable flow (R10):** the existing "My player card" screen (`MyPlayerCard.jsx`) gains these fields, with a live card preview, validation messages that match the server, and loading, empty, success and error states. World Cup is untouched.

**Completion checks:**
- A linked player updates their display name, portrait, rating, attributes, preferred foot and play style, and the public roster, player profile and card show the new values.
- The same call is refused for another player's card, an unlinked account, an anonymous caller, and any attempt to change team, season, jersey number, position, legal name, roll number, email or the account link.
- Out-of-range ratings or attributes and non-catalog play styles are refused with a clear message, and nothing changes.
- Captain and dictator edits of the shared fields still work. Every change by any role writes one audit row with no email in it.
- Verified through the real UI → Worker/Data API → database path, locally and in the staging release-candidate walkthrough.
