**Consolidated (2026-11-18):** absorbs SL-033 (Supabase access for Workers). A Worker cannot serve anything until its database and Auth access path is decided, so the runtime and the access path are one foundation.

**Issue:**
- The deployed backend is Next.js/Vercel. There is no Worker runtime, Wrangler config or Hono service boundary.
- The current backend uses Next server clients, cookies, direct Supabase JS calls and service-role secrets, and those assumptions do not transfer to Workers automatically.
- Moving all routes in one step risks losing working features.

**Required outcome:**
- Define the Cloudflare Worker entry points, Hono application structure, runtime-compatible dependencies, environment bindings, observability and error conventions, and the deploy process.
- Draw service boundaries from the Phase 2 domains and contracts (SL-026). Decide the count from independent deployment and ownership needs (D-05); do not use "32" as an unvalidated target.
- Select and document the supported database and Auth access path for Workers (D-04): token forwarding, transaction and connection strategy, and how privileged operations are scoped. Keep Supabase Auth, but do not assume a Node-specific driver or Next cookie behavior works unchanged.

**Completion checks:**
- A local Worker starts with non-production configuration and calls only the local or test Supabase project.
- Auth validation and scoped user identity are tested.
- Gateway and service health are observable.
- Database limitations, connection strategy and privileged operations are documented.
- No Cloudflare private credential is checked in.
- The current frontend stays functional against its existing API while the migration proceeds.

**Usable in its own phase (rule R10):** not applicable (backend runtime infrastructure).
