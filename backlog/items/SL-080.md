**Status:** Implemented and in use (2026-11-19). `.github/workflows/db-deploy.yml` deploys `develop` to staging with the synthetic seed and `main` to production migrations-only, behind the required reviewer and a verified pre-migration backup (`docs/backups.md`). The first production run was approved and succeeded: Database deploy run `44610257088` applied all 19 pending migrations (through `20261130000007`) after confirming backup `automated-prod/pre-migration/20261119T203759Z-44610257088-1.dump.age`. Production already had a migration history, so the history repair was not needed. Remaining: the owner attests C4 (`pnpm work attest SL-080 C4`), then `pnpm work done SL-080`.

**Issue:** No migration workflow exists. Applying migrations from both branches without environment separation could accidentally change production or mix development data.

**Required outcome:** Add CI to validate migrations and seed against local Supabase. On pushes/deployments to `develop`, target only an explicitly configured development Supabase environment. On `main`, target production only through a protected GitHub Environment requiring the configured approval and backup/release checks. Never run `db reset`, `db seed`, or `--linked` against production as part of deploy automation.

**Completion checks:** The workflow logs the target environment/project identity without secrets; develop and production secrets are separated; failed migration stops deployment; production requires an explicit protected approval; local CI proves a fresh migration path.
